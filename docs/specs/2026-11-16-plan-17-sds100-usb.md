# Plan 17: The SDS100 over USB — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner's SDS100 works as a USB station in the command line and the Mac app the way
the SDS150 does, with its status pushes kept going by sending its `PSI` again every 60 s.

**Architecture:** One connection stack for both handhelds. `PushKeepAlive` gains a second kind,
"renew the subscription", which `ScannerClient` writes through the existing keep-alive loop; the
SDS100 becomes a third `ModelProfile` and a third mock personality; ports are labeled by USB
product name because the two handhelds share a product ID. Nothing about how a station finds its
port changes.

**Tech Stack:** Swift 6, Swift Testing, SwiftPM; the existing `NoctuleKit`, `NoctuleStore`,
`NoctuleAppCore`, `NoctuleCLICore`, `NoctuleMockScanner` targets. No new dependency.

**Spec:** `docs/specs/2026-11-16-sds100-usb-design.md` (read it first; § numbers below are its).
Plan 16 is reserved for PR checks (`2026-11-14-release-manager-design.md`), hence 17.

## Global Constraints

- Branch `feature/sds100-usb`. Tests first, against the mock; developer and QA per task, with a
  mutation run showing each new test fails against the pre-change code.
- Every shell that builds, tests or runs `noctule` has `NOCTULE_NO_USB_DETECTION=1` exported.
  `noctule station`, `log` and `hits` always get `--settings-dir <temporary directory>`. The app
  is launched only with `NOCTULE_SETTINGS_DIR` on a temporary directory whose stations are mocks.
- **No task opens a real scanner.** Two real handhelds are on USB (an SDS150 and an SDS100, both
  vendor 0x1965 product 0x001A). Never open, read, write or `stty` a `/dev/cu.usbmodem*` path;
  tests pass the mock's path and their own port listing. Task 9 is the owner's.
- Never `KAL`, `MSM,1`, `POF` or a guessed command to an SDS100, in code or tests' expectations of
  the product. The product never sends `GCS` to an SDS100.
- The SDS150's behaviour is unchanged byte for byte: `KAL` every 60 s, never a repeated `PSI`.
  The SDS200's is unchanged.
- No real system, site or channel names, frequencies or IDs in tracked files; `RealNamesTests`
  must pass. Fixtures and mock values are fictional.
- No test is loosened: a test that pinned the SDS100's old values pins the new ones; a test whose
  point is "a model without a keep-alive" or "a model at 500 ms / 1 s" moves to `BCD436HP`.
- Shared code builds for iOS: `xcodebuild -scheme NoctuleAppCore -destination 'generic/platform=iOS' build`.
- The values: renewal every **60 s**; SDS100 `pushInterval` **100 ms**, `displayRefreshInterval`
  **100 ms**, levels **0–15**, `usbProductIDs` **[0x001A]**, `protocolVerifiedOnHardware`
  **false**; mock firmware **`Version 1.26.01`**, push lifetime **183 s**, glyph bytes
  **0x06, 0x07, 0x1A, 0x1B**.
- Update `LESSONS.md` during the work whenever something surprises you.

## Review Focus

1. **A renewal after `PSI,0`.** A stray `KAL` after a stop is harmless; a stray `PSI,<ms>` starts
   the pushes again and leaves a live subscription on the radio after quit. A stop, a consumer
   cancel, a disconnect or a newer push that lands while a renewal is due or waiting for the
   request slot must write no renewal. (Task 1, Step 1, tests c–e; Task 6's end-of-run checks.)
2. **A renewal at the old rate after a newer push.** When a push is started again at another
   interval, the earlier push's loop must never write its old `PSI,<ms>`: it would change the
   rate under the new subscription. (Task 1, test f.)
3. **A renewal while the app is busy.** With `STS` read every 100 ms and menu reads every 2 s the
   request slot is rarely free; renewals must still go out well inside the 183 s. (Task 5, test
   `sds100RenewsWhileTheDisplayLoopIsBusy`.)
4. **A `PSI,NG` whose owner is unclear.** A rejection before any renewal was written ends the push
   (no subscription exists); one after a renewal keeps it. (Task 1, tests g–h.)
5. **The other handheld behind a station's port.** An SDS100 station whose port, after a replug,
   holds a scanner that says `SDS150` must not subscribe: the existing "a different scanner
   answered" rule, pinned for this pair so neither keep-alive reaches the wrong model. (Task 5,
   test `sds100StationRefusesAnSDS150OnResume`.)

  - In `ModelProfileTests`: `PushKeepAlive(command: "KAL", interval: .seconds(60)).action == .command("KAL")`,
