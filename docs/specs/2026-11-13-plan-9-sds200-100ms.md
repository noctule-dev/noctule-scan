# Plan 9 — The SDS200 at 100 ms — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On an SDS200, the app and `noctule log` subscribe with `PSI,100`, and the app reads `STS` at most once per 100 ms while the screen changes, the SDS150's rates.

**Architecture:** The rates are already per-model data (`ModelProfile.pushInterval`, `displayRefreshInterval`), read by `StationRunner` and `DisplayRefreshPolicy(model:)`. The SDS200's two values change, and so do the tests that pin them, the comments that state them, and the docs. No new code path. The branch merges only after the owner's hour-long hardware run.

**Tech Stack:** Swift 6, Swift Testing, `MockSDS200` and the existing client stack.

**Spec:** `docs/specs/2026-11-13-sds200-100ms-design.md` (approved by the owner 2026-11-13). Read all of it before any task; §2's anti-goals govern every test change.

**Branch:** `feature/sds200-100ms` (already created from `main`; the spec and this plan are its first commit). The throwaway `spike/sds200-100ms` (`b064dfa`) is not merged or built on; it is deleted after this branch merges.

## Global Constraints

- SDS200: `pushInterval: .milliseconds(100)`, `displayRefreshInterval: .milliseconds(100)`. SDS150 unchanged (100 ms, 100 ms). SDS100 and BCD436HP unchanged (500 ms, 1 s). A name that is no known model: `StationRunner` still subscribes at 500 ms.
- `noctule watch --interval` keeps its default of 500 ms for every model.
- `DisplayRefreshPolicy`'s other values are unchanged: `maxInterval` (5 s), `afterKey` (150 ms), `menuMinInterval`, `menuIdleInterval`, `menuMaxKeyDeferral`.
- No test is widened to accept both old and new values. A test that pinned 500 ms or 1 s for the SDS200 pins 100 ms; any other failure the faster rate causes is understood and reported before the test is changed (spec §2, §5).
- Every shell that runs `swift test` or `noctule` has `export NOCTULE_NO_USB_DETECTION=1`. No agent runs anything against the owner's SDS200 or SDS150 in this plan; Task 3 is the owner's.
- No real radio traffic in tracked files (`RealNamesTests`); no owner-specific values.
- Strict TDD per the repo's workflow: a failing-test commit, then a passing-implementation commit. QA re-runs the developer's commands, checks the RED commit fails as claimed, and proves new tests with a mutation (restore the old value in a temporary worktree; the test must fail). Forbidden mutations: none that could reach hardware (this plan touches no hardware path, but QA runs nothing without the kill-switch).

## Review Focus

1. **A scanner whose `MDL` names no known model, on a network station:** `StationRunner` must still send `PSI,500`, not follow the SDS200's new rate. Pinned in Task 1 (`networkStationOfAnUnknownModelSubscribesAt500ms`).
2. **The SDS200's other display timings:** only `minInterval` moves. An unchanging screen is still read every 5 s, and the menu timings are the default's. Pinned in Task 1 (`modelsPolicy` assertions for `.sds200`).
3. **A model left at the old rate:** with both real radios at 100 ms, nothing would notice the 1 s path breaking. Pinned in Task 1 (the SDS100 at 1 s in `modelsPolicy`).
4. **`watch` on any scanner:** still `PSI,500` by default. Already pinned by `WatchIntegrationTests` and `MockScannerIntegrationTests` (`control: PSI,500`); Task 1 checks they still pass, unchanged.
5. **App sessions on `MockSDS200` with a live display loop:** ten reads a second could shift a count or a timing in `NoctuleAppCoreTests`. Task 1 runs the whole suite; any such failure is reported to the controller with its cause before anything is changed.
