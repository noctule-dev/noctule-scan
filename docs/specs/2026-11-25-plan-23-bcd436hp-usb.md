# Plan 23: the BCD436HP over USB — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the BCD436HP a fully supported USB handheld in `noctule` and the Mac app, on the SDS handhelds' stack, and give every handheld (SDS100, SDS150, BCD436HP) a Scanner view panel with only the keys it has, as the approved design describes (§5.11 for the SDS handhelds).

**Architecture:** The BCD436HP becomes a fourth `ModelProfile` whose differences are data: the SDS100's renewal keep-alive, `MNU`/`MSB` menu navigation, a 24-column display with no soft-key line, Hold by `HLD`, its own key set and destructive items. A fourth mock personality reproduces every hardware fact of design §3 so each product path is tested on the mock first. No BCD-specific handlers: `MenuModel`, `DisplayModel`, `StationSession` and the views read the profile.

**Tech Stack:** Swift 6, SwiftUI/AppKit (views only), Swift Testing, the repo's `noctule-mock-scanner`.

**Spec:** `docs/specs/2026-11-25-bcd436hp-usb-design.md` (approved 2026-11-25). Read §3 (hardware facts) and §5 (design) before any task.

## Global Constraints

- Every shell that runs `noctule`, tests or the app: `export NOCTULE_NO_USB_DETECTION=1`. Agents never open the real BCD436HP (or any `/dev/cu.usbmodem*`) during this plan; all work is on the mock. The hardware session (design §7) is the owner's, after the build.
- Every commit `git commit -s` (DCO), ending with the session's attribution trailer.
- Every new `.swift`, `.sh`, `.py`, `.yml` file starts with the two-line SPDX notice (`AGENTS.md`, Working rules).
- Every new `@Suite` has a `.timeLimit`.
- No real names, frequencies, indexes or coordinates in code, fixtures, tests or docs; the mock's text is fictional.
- Model knowledge lives in `ModelProfile` (or `MockPersonality` for the mock), never in `if model == .bcd436hp` branches in shared logic.
- The product never sends `KAL`, `GCS`, `MSM` or `POF` to a BCD436HP, and never `MNU`, `MSB` or `HLD` to an SDS model.
- Nothing the SDS200 sends or draws changes. The SDS100 and SDS150 change only as design §5.11 says: no `KEY,T`/`KEY,Q` (SDS150: nor `KEY,R`), and their encoder push captioned Vol.
- Exact strings: enter `MNU,TOP,`; back `MSB,,`; exit `MSB,,RETURN_PREVOUS_MODE` (Uniden's spelling); Hold `HLD,SYS,<i>,`, `HLD,DEPT,<i>,<system i>`, `HLD,TGID,<i>,`, `HLD,CFREQ,<i>,`.
- BCD436HP values: volume and squelch `0...15`; push interval 100 ms; display refresh 100 ms; keep-alive `PushKeepAlive(action: .renewSubscription, interval: .seconds(60))`; display 24 columns, no soft-key line; mock `MDL,BCD436HP`, `VER,Version 1.28.24`.
- `MenuModel`'s rules hold for the new commands: `GSI` before enter and exit, one state-changing command per action, never resent, refused while busy, withheld at the slot once detached (`SendPermit`).

## Plan-time refinements of the design (the designer's calls, for the owner to see)

1. **`Rssi` (§5.4):** `ScannerInfo` already parses `Rssi` as an integer, so the BCD's decimals (`1.267`) are already nil. No `rssiReading` profile field; a test pins it.
2. **Hold re-read (§5.3):** the next push (every ~160 ms) shows the hold state; no extra `GSI` is sent after an `HLD`. A Hold click is refused while an `HLD` is in flight.
3. **Channel hold and ID search (§5.3):** on hardware `HLD,TGID,<index>,` held a programmed talkgroup on a system in ID search. So the Channel control is disabled only for an unprogrammed talkgroup (index `ScannerInfo.unprogrammedIndex`), whose hold would need `STGID` (untried), not for ID search as a whole.
4. **Soft-key chords (§5.3):** on the BCD436HP the codes `A`, `B`, `C` *are* its System, Dept and Channel keys, so a key-map chord bound to Soft key 1–3 presses those keys (same code, same key), instead of being dropped. Chords for keys the model lacks (`T` Services, `Q` squelch push) are dropped.
5. **The knobs** (design §5.11, which also covers the SDS100 and SDS150). The handhelds have one multifunction encoder on top (the owner, 2026-11-25): turning it scrolls (`>`/`<`), one press makes turning set volume, Func then a press makes it set squelch; its press is `^` ([spec] V1.05). The Scanner view keeps its direct VOL and SQL knobs on the BCD436HP (one `VOL,<n>`/`SQL,<n>` each, never leaving the radio in a level mode), and its SCROLL knob stands for the encoder: the push still sends `^`, captioned **Vol**, with the help text "Press: volume. Func, then press: squelch." The squelch knob has no push (`Q` isn't on the BCD436HP); the volume knob's push stays `V` (Backlight, "Light").

## Review Focus

1. **A double-click on a Mac-style Hold button** would send two `HLD`s and toggle the hold straight back off: a click while an `HLD` is in flight sends nothing (Task 8).
2. **An Exit whose `GSI` was stale** (the radio left the menu from its own panel): `MSB,,RETURN_PREVOUS_MODE` answers `MSB,NG`; the user sees the menu close, no warning loop, and no `KEY,L,P` (Avoid) is ever sent (Task 6).
3. **Hold on an unprogrammed talkgroup** must not send `HLD,TGID,4294967295,`: the Channel control is disabled there (Task 8).
4. **The first `STS` before `MDL` names the model:** the display must switch to the BCD layout once connected, never show three soft-key labels made from line 14 (Task 7).
5. **`noctule display` over the network** must keep sending only `STS` (no `MDL` added), and keep its soft-key line (Task 7).
