# Plan 7 — SDS150 over USB: protocol, mock and command line — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. This repo's workflow (AGENTS.md, Plans 1–6) applies on top: feature branch `feature/plan-7-sds150-usb`, tests first, a commit per task, mock before hardware, `LESSONS.md` updated as things surprise you. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `noctule info|status|display|watch|log` work against an SDS150 connected by USB serial, developed and tested on a serial mock, with no audio.

**Architecture:** `NoctuleKit` gains a byte-stream reply assembler, a POSIX serial `ScannerTransport` and a USB port finder beside the UDP ones; `ModelProfile` carries what differs between models. `StationRunner` builds its transport from the station's connection, skips everything about audio for a USB station, and waits for the port and resumes when the scanner goes away. The mock's control core is made peer-neutral so the same command handling answers on a pseudo-terminal with an SDS150 personality.

**Tech Stack:** Swift 6, Swift Testing, POSIX `termios` and pseudo-terminals, IOKit (macOS only), the existing client stack and mock.

**Spec:** `docs/specs/2026-11-11-sds150-usb-design.md` (approved by the owner 2026-11-11). This plan is its stage 1 (§4, §5, §6, §8 checks 1–6 and 8). The app (§7) is Plan 8. Read the spec's §3 before any task.

## Global Constraints

- **Agents send nothing to the owner's SDS150 in this plan** except in Task 10, with the owner present and their go-ahead for each check. The scanner is attached to this Mac: no test, script or command may open a `/dev/cu.usbmodem*` or `/dev/tty.usbmodem*` path, and every test or integration run that needs a port passes the mock's pseudo-terminal path explicitly, so automatic detection can never pick the real scanner.
- Never send `MSM,1` or `POF` to a serial scanner. No guessed or undocumented commands. Commands used: `MDL`, `VER`, `VOL`, `SQL`, `GSI`, `STS`, `PSI`, `KEY`, `MSI`, `MSV`, `GCS`.
- One action sends at most one state-changing command and never resends it; a timeout is answered by a re-read. A failed or short serial write is an error, not a retry.
- Every `PSI` subscription ends with `PSI,0` on every exit path.
- A USB station never creates an `AudioSession` and never reads, waits on or writes the RTSP cooldown store.
- Line settings: 115200 baud, 8 data bits, no parity, 1 stop bit, no flow control. Uniden's USB vendor ID is `0x1965`; the SDS150's serial-mode product ID is `0x001A`.
- Hint text, exact: `Plug the scanner in and choose Serial Port on its screen.`
- `SerialTransport` and the IOKit finder are macOS only (`#if os(macOS)`). `NoctuleKit`, `NoctuleStore` and `NoctuleAppCore` must still build for iOS: `xcodebuild -scheme NoctuleAppCore -destination 'generic/platform=iOS' build`.
- No real radio traffic in tracked files: fixtures use the fictional names given in this plan (`Lakeview County`, `County Roads`, …). `RealNamesTests` must pass. The brainstorm's probe output is real traffic and must not be copied.
- Model-specific facts go in `ModelProfile` or the mock's personality, not in branches on the model.
- Nothing the network path does today may change: the whole existing test suite passes after every task.

## Review Focus

Conditions the spec implies that a person will meet; each has a test in the task named.

1. **The port is already open in another program** (a second `noctule`, a browser's Web Serial, a terminal program): the command fails at once with a message that says the port is in use; it does not hang or share the port. → Task 3, Task 9.
2. **The scanner leaves mid-command** (cable pulled, switched to mass storage, battery flat): the in-flight command times out, is not resent, open hits are closed and logged, and `stop()` still returns promptly even though `PSI,0` can't be delivered. → Task 7.
3. **Leftover or partial bytes when the port opens** (half a reply from a previous session, a truncated XML document): nothing is delivered as an answer to the first command. → Task 1, Task 3.
4. **A different scanner answers after a resume** (another Uniden model plugged into the same cable): the station does not resume into it; it keeps waiting and says why once. → Task 7.
5. **Two Uniden scanners attached and no port chosen**: nothing is picked arbitrarily; the message says to choose a port. → Task 4.

**Interfaces:**
- Consumes: `ResponseLineParser.parse(_:)`, `ScannerResponse`, and the XML parsing `UDPDatagramAssembler` uses.
- Produces:
  ```swift
  public struct SerialResponseAssembler {
      public init(now: @escaping @Sendable () -> ContinuousClock.Instant = { .now },
                  maxDocumentAge: Duration = .seconds(10),
                  maxDocumentBytes: Int = 4_194_304,
                  maxLineBytes: Int = 65_536)
      public mutating func ingest(_ bytes: Data) -> [ScannerResponse]
  }
  ```

Rules the tests pin (spec §4.2):
- Lines end at `\r` or `\n`; empty lines are dropped; text is decoded as lossy UTF-8 with NUL removed, as `UDPDatagramAssembler` does.
- A line ending `,<XML>,` opens a document for the command before the first comma. The root element is the first element that isn't the `<?xml …?>` declaration; the document ends at the line `</Root>` or when the root is self-closing on its own line. It becomes `.xml(command:root:)`. A `<Footer …/>` or `<Foot …/>` child is removed from the root.
- A new `,<XML>,` header while a document is open abandons the open one and starts the new.
- A document older than `maxDocumentAge` (checked on each `ingest`) or larger than `maxDocumentBytes`, an unparsable document, and a line longer than `maxLineBytes` are dropped; the assembler returns to line mode and keeps working.

Behaviour (spec §4.1): `open()` closes any earlier link, opens `path` with `O_RDWR | O_NOCTTY | O_NONBLOCK`, sets raw 115200 8-N-1 with `CLOCAL | CREAD` and no flow control, takes `TIOCEXCL`, and flushes input. `ENOENT` → `.noSuchPort(path)`; `EBUSY` → `.busy(path)`. Read bytes go through one `SerialResponseAssembler` per open. A read of 0 bytes or `ENXIO`/`EIO` finishes `responses`. `send` writes all of `wireBytes` or throws `.writeFailed`; it never retries. `responses` is a fresh stream per `open()`, as `UDPTransport` does it.
