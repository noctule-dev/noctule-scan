# Plan 8 — The app for the SDS150 over USB — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. This repo's workflow (AGENTS.md, Plans 1–7, memory `dev-workflow`) applies on top: feature branch `feature/plan-8-sds150-app`, a failing-tests commit before each implementation commit, a developer subagent and a QA subagent that reruns everything, mock before hardware, a ledger in `.superpowers/sdd/2026-11-12-plan-8-sds150-app/progress.md`, a whole-branch review before the pull request, `LESSONS.md` updated as things surprise you. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A USB station (the SDS150) opens in the Mac app and works as a network station does today, minus audio: display, keys, volume and squelch, menus, hit logging, a battery reading, and a wait-and-resume when the scanner is unplugged.

**Architecture:** `StationSession` stops refusing USB stations and runs them through the same `StationRunner` the CLI uses, with a port listing handed in by the app shell behind the same kill-switch as the CLI. A new phase, `.waitingForScanner`, covers both "not plugged in yet" and "went away", so the window always has one thing to show and one way out. Before the app is touched, three holes Plan 7 left are closed in shared code (what "receiving" means, the keep-alive next to other commands, a subscription that died during a pause), because the app polls the scanner far more than `noctule log` does.

**Tech Stack:** Swift 6, SwiftUI and AppKit (macOS), Swift Testing, `MockSerialScanner` on a pseudo-terminal, the existing client stack.

**Spec:** `docs/specs/2026-11-11-sds150-usb-design.md` (approved by the owner 2026-11-11). This plan is its stage 2: §7, with §13 P's open items and hardware check 7. Read §3, §4.5, §7, §8's results table and §13 before any task. The handoff this plan was written from is `.superpowers/sdd/2026-11-12-plan-8-sds150-app/HANDOFF.md`.

## Global Constraints

- **Agents and tests never reach the owner's SDS150.** Every shell exports `NOCTULE_NO_USB_DETECTION=1`; every `noctule station|log|hits` gets `--settings-dir`; the app is launched only with `NOCTULE_SETTINGS_DIR` pointing at a temporary directory whose only stations are mocks. No test resolves "the only Uniden port": tests pass the mock's link path and their own `ports:` listing. No one opens, reads, writes or `stty`s a `/dev/cu.usbmodem*` or `/dev/tty.usbmodem*` path.
- **QA mutations that are forbidden** (they could reach hardware if the guard under test is what protects it): removing the kill-switch or private-settings checks of Task 4 while running anything but unit tests; any mutation run with detection on. Subprocess tests launch from a temporary directory.
- Never `MSM,1` or `POF` over serial. `KAL` only from the push keep-alive, only to a model that has one, only over serial. No guessed commands. Commands the app sends to a USB scanner: `MDL`, `VER`, `PSI`, `KAL`, `STS`, `GSI`, `MSI`, `GCS`, and, only on a user's action, `KEY`, `MSV`, `VOL,<n>`, `SQL,<n>`.
- One action sends at most one state-changing command and never resends it. A failed or short serial write is an error, not a retry.
- Every `PSI` subscription ends with `PSI,0` on every exit path; the serial mock's `activeSubscribers` is 0 after every test.
- A USB station never creates an `AudioSession` and never reads, waits on or writes the RTSP cooldown store.
- The hardware task (12) runs only with the owner's say-so. Standing instructions (2026-11-12): agents may run the read-only commands, `watch`, the opt-in suites and `log` on the `sds150` station; each `KEY`, `MSV`, `VOL`/`SQL` set, the first `MSI`, and the first launch of the app against the SDS150 need a go-ahead each time. Cable, transmitting and sleeping the Mac are the owner's.
- Hint texts, exact: `Plug the scanner in and choose Serial Port on its screen.` (`SerialPort.noneFoundHint`), `More than one Uniden scanner is connected. Choose its port.` (`severalFoundHint`), `The scanner is connected but isn't sending status updates.` (`notSendingUpdatesHint`). Status bar, exact: `No audio over USB`.
- `NoctuleKit`, `NoctuleStore` and `NoctuleAppCore` build for iOS after every task: `xcodebuild -scheme NoctuleAppCore -destination 'generic/platform=iOS' build`. Nothing under `NoctuleAppCore` imports IOKit, AppKit or SwiftUI.
- No real radio traffic in tracked files, ledgers or memory. Fixtures use the fictional names already in the repo (`Lakeview County`, `County Roads`, `Road Crews`, `Plow Dispatch`). `RealNamesTests` passes.
- Model facts live in `ModelProfile` or `MockPersonality`, not in branches on the model.
- Nothing a network station does today may change: the whole suite passes after every task (1236 tests at the start).

## Review Focus

Conditions the spec implies that a person will meet; each has a test in the task named.

1. **The window opens with the scanner unplugged** (the app reopens the last station at launch; a handheld is usually in a pocket): the window says it is waiting and how to fix it, opens nothing, and connects by itself when the port appears. → Task 5.
2. **The user gives up while it waits** (Stations in the banner, Disconnect, ⌘W, Quit, the Mac going to sleep): each returns within a second, sends nothing, and leaves no subscription and no open port. → Task 5, Task 11.
3. **A second station, or `noctule log`, wants the same scanner**: the second one says who has it and opens nothing; Test Connection on a station whose own window holds the port says to disconnect first, not "another program". → Task 7, Task 8.
4. **The scanner is unplugged in the middle of a menu, a held key or a level change**: nothing queued is sent to the scanner when it returns, the menu closes, and the window recovers. → Task 5.
5. **A wrong or silent device on the port** (another Uniden model, a scanner in a state where it doesn't answer): the window keeps waiting and shows the runner's warning once; it never opens the port once a second. → Task 5 (the runner's bound, shown through the session).

  // ScannerClient: both push starters gain one parameter, default nil
  public func startPushUpdates(interval: Duration = .milliseconds(500), keepAlive: PushKeepAlive? = nil,
                               onKeepAliveFailure: (@Sendable (any Error) -> Void)? = nil) async throws -> AsyncStream<PushUpdate>

  // PushKeepAlive
  /// What an interval override may be: 0.05 s to 60 s. `forSubscription` ignores one outside it.

- `writeKeepAlive` acquires the request slot before its checks and its write and releases it after, so a keep-alive is written only between a reply (or timeout) and the next request. The checks (`!Task.isCancelled`, connected, this push still the active one) run after the slot is held. A stop that arrives while a keep-alive waits for the slot writes its `PSI,0` after the slot frees and the keep-alive writes nothing.
- A keep-alive write that throws calls `onKeepAliveFailure` once with the error, on its way out of the loop; nothing is retried (unchanged).
- `PushKeepAlive.forSubscription(reportedModel:overSerial:interval:)`: an `interval` outside `overrideRange` is ignored (the model's own interval stays). `KeepAliveOverride.range` in `NoctuleCLICore` becomes this one range.

- Runner rule, added to the tick: on a `usbSerial` station, while `connected`, when this connection has delivered a push, its subscription was started with a keep-alive (whether or not a write of it has failed since), and no push has arrived for one keep-alive interval (the model's, or `keepAliveInterval`), the runner emits `.warning(resubscribingMessage)` and ends the subscription with `client.stopPush()` (a failure is ignored). It happens once per connection: a resumed connection resubscribes only after it has delivered a push of its own. A network station and a model without a keep-alive never resubscribe.
- A failed keep-alive write is `.warning(keepAliveFailedMessage(error))`, once per subscription; the stall rule above then replaces the subscription.
- `KeepAliveOverride`: with `NOCTULE_TEST_KEEPALIVE_SECONDS` set and `NOCTULE_NO_USB_DETECTION` unset or empty, the note is `ignoring NOCTULE_TEST_KEEPALIVE_SECONDS=<value> (it needs NOCTULE_NO_USB_DETECTION set)` and the model's interval stays.
