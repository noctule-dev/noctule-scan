Labels: **(owner)** marks what the owner decided in the brainstorm; **(designer's call)** marks a default the owner hasn't ruled on and can overturn; **(designer's call during the build)** marks one made while stage 1 or stage 2 was built (§13), also the owner's to overturn. **[hw]** marks a fact seen on the owner's SDS150 on 2026-11-11 (firmware 1.01.02); **[spec]** marks Uniden's *SDS Series Remote Command Specification* V2.00 (2025-07-07; local copy in the git-ignored `docs/uniden/`); **[assumed]** marks something neither has shown.

## 1. Why

Noctule Scan works with the SDS200 over the network. The owner also has an SDS150, a handheld with no network port, connected to the Mac by USB. The original design (§5) always meant USB serial to be the second transport; `TransportKind.usbSerial`, an SDS150 `ModelProfile` and `StationDeviceSettings.usbPort` already exist, unused. This design fills that in.

## 2. Goals, non-goals, anti-goals

Goals:

1. An SDS150 connected by USB works as a station the way the SDS200 does today: commands, the mirrored display, keys, volume and squelch, status pushes, menus, hit detection and the hit log. **(owner: "it should work just like it is working today")**
2. Protocol support over USB comes first; the app follows. **(owner; the two-stage split in §9 is the designer's reading of it)**
3. The SDS150's screen is drawn from what the scanner reports (`STS`), with the same logic as the SDS200's, because the user can customize the screen on every SDS model. No per-model screen layout. **(owner)**
4. Everything is developed against the mock first (AGENTS.md rule), so the mock gains a serial connection and an SDS150 personality. **(designer's call, from the repo's rule)**
5. The serial transport is model-neutral, so the SDS100 and the SDS200's USB port can use it later without redesign. **(designer's call)**

Non-goals (this spec):

- **Audio from the SDS150.** The USB connection is a serial port only **[hw]**, the command specification has no audio command **[spec]**, and Bluetooth is undocumented. Listening and recordings for the SDS150 are a later spec. **(owner)**
- Bluetooth of any kind.
- The SDS100 and BCD436HP as tested, supported models. They may happen to work.
- The SDS200 over USB as a supported setup. (It would have control over USB and no audio; nothing here forbids it, nothing here tests it.)
- New commands the app doesn't use today: `POF` (power off), `MNU`/`MSB` (direct menu jumps), `URC` (scanner-side recording), waterfall (`GST`, `PWF`, `GWF`, `GW2`). (`KAL` was listed here; since the hardware session it is the push keep-alive, §13 O.)
- iPhone and iPad. They can't open USB serial; the shared code must still build for iOS.
- An SDS150 drawing of the front panel. The Scanner view keeps its current panel for every model for now. **(designer's call; see §7.3)**

Anti-goals:

- A USB station must never open, wait on, or write the RTSP cooldown machinery. It has no audio server.
- `MSM,1` must never be sent to an SDS150. The owner's approval of that undocumented command was for the SDS200, and it is not in **[spec]**.
- No real system, channel or frequency names from the owner's SDS150 in tracked files. The probe output from the brainstorm is real traffic and stays out of the repo.

## 3. What we know

### 3.1 The USB device **[hw]**

- The scanner does not appear on USB at all until the user answers its on-screen prompt (serial port or mass storage). In serial mode it enumerates as "SDS150 Serial Port", vendor "UNIDEN AMERICA CORP.", vendor ID 0x1965, product ID 0x001A, USB 2.0 full speed.
- One configuration, two interfaces: CDC abstract control (class 2, subclass 2) and CDC data (class 10). No audio interface, no network interface. macOS's built-in CDC ACM driver binds it and creates `/dev/cu.usbmodem<serial>1` and the matching `tty.` node. No third-party driver.
- The USB serial number looks like a placeholder (zeros and a 1), so it may be the same on every unit. Don't rely on it to tell two SDS150s apart.
- Mass-storage mode is a different USB personality and was not examined.

### 3.2 The protocol over serial

| Item | Finding |
|---|---|
| Line settings | 115200 baud, 8-N-1, no flow control worked **[hw]**. **[spec]** doesn't state them. A CDC ACM device usually ignores the baud rate **[assumed]**. |
| Command framing | `NAME[,args]\r`, same bytes as UDP **[hw]** |
| Reply timing | First byte within 1–20 ms for `MDL`, `VER`, `VOL`, `SQL`, `GSI`, `STS` **[hw]** |
| `MDL` | `MDL,SDS150` **[hw]**. **[spec]** says `SDS150GBT`. Accept both (`ScannerModel(reported:)` already does). |
| `VER` | `VER,Version 1.01.02` **[hw]** |
| `VOL`, `SQL` | Plain number replies **[hw]**; range 0–15 for SDS100/SDS150 **[spec]** |
| `GSI` | `GSI,<XML>,\r` then the XML document as CR-separated lines, ending `</ScannerInfo>\r`. **No `<Footer>` element** (UDP has one) **[hw]**. Same structure as the SDS200: `MonitorList`, `System`, `Department`, `ConvFrequency`, `DualWatch`, `Property`, `ViewDescription`. `Property` carries `VOL`, `SQL`, `Sig`, `Rssi`, `Mute`, `Att`, `Rec`, `P25Status`, plus `Backlight`, `A_Led`, `Dir`, `KeyLock`, `F`. One difference found on 2026-11-12: a conventional channel's `Freq`, `Mod` and `SAD` are attributes of `ConvFrequency` itself, with no `Site` or `SiteFrequency` **[hw]** (§8, check 8). |
| `STS` | One CR-terminated line: display-form digits, then a text field and a mode field per line, then trailing fields. The reply seen had 17 lines of 30 characters and the soft-key line last, with the same three soft-key mask columns the SDS200 uses **[hw]**. The line count depends on the user's screen, so nothing may assume 17. Some text fields hold bytes that aren't valid UTF-8 (icon glyphs) **[hw]**. |
| `GCS` | `GCS,CST=n,VOLT=nnnnmV:nn%,CURR=nnnnmA,TEMP=nn.nnC` terminated by **`\n`**, not `\r` **[spec]**. Sent on 2026-11-12: it answers and parses, with `CST=8` at 100 % on USB power, a code outside the spec's 0–6 **[hw]**. |
| `PSI` | Same form as the SDS200 **[spec]**. Sent on 2026-11-12: accepted, pushes at the rate asked, `PSI,0` stops them **[hw]**. **The pushes stop by themselves 183 s after the `PSI`**, port still open **[hw]** (§8, check 6). |
| `KAL` | `KAL\r`, "Keep Alive", no reply **[spec]**. Sent every 60 s while a subscription runs, to keep the pushes going (§13 O). On 2026-11-12 it did, for 240 s, 300 s and an hour, and nothing came back for it in the 240 s check, which reports every line that isn't a push **[hw]** (§8, check 15). As built in Plan 8 it is never written while another command's reply is pending (§13 U). |
| `KEY`, `MSI`, `MSV` | Same forms as the SDS200 **[spec]**. Not sent over serial yet. |

### 3.3 What is not known

Listed as hardware checks in §8. The main ones: `PSI` pushes over serial, whether a push can arrive in the middle of another reply, what the scanner does when the Mac closes the port, and whether the link needs `KAL` to stay up. §8 has the answers found so far: it needs something (check 6), and `KAL` every 60 s keeps it pushing, for an hour when tried (check 15).

## 4. Shared code (stage 1)

### 4.1 `SerialTransport`

A new `ScannerTransport` in `NoctuleKit/Transport/`, next to `UDPTransport`, honoring the same contract (`open`, `send`, a fresh `responses` stream per `open`, `close`, reopenable).

- POSIX `open` of the callout device (`/dev/cu.…`) with `O_RDWR | O_NOCTTY | O_NONBLOCK`, then `termios` raw mode, 115200 8-N-1, `CLOCAL | CREAD`, no flow control, and `TIOCEXCL` so a second process gets `EBUSY` instead of sharing the port. **(designer's call)** As built, exclusive use is two locks, `TIOCEXCL` and a `flock` (§13 D).
- Flush input on open, so a half-read reply from a previous owner of the port can't be mistaken for an answer.
- A read loop feeds bytes to the assembler (§4.2). `read` returning 0 or `ENXIO`/`EIO` (the device went away) finishes `responses`; the session above treats that as it treats a finished UDP stream today. As built, so does a hang-up that `poll` reports while `read` has nothing, on three polls in a row 10 ms apart (otherwise the reader would spin and the stream never finish), and a requested close first waits, bounded, for the output queue to empty (§13 M).
- `send` writes the command's `wireBytes` whole. A short or failed write is an error to the caller; it is not retried (the never-resend rule, §4.6).
- Errors mirror `UDPTransportError`: not open, no such port, busy (held by another process), open failed.
- **macOS only.** The file is under `#if os(macOS)`; on iOS a station whose transport is `usbSerial` fails to start with a clear "not supported on this device" error. `NoctuleKit`, `NoctuleStore` and `NoctuleAppCore` must still pass the iOS build in AGENTS.md. **(designer's call)**

### 4.2 `SerialResponseAssembler`

Serial is a byte stream, so reply boundaries have to be found. A pure value type like `UDPDatagramAssembler`, never throwing, unit-tested with bytes split at every possible position.

- Bytes are cut into lines at `\r` or `\n` (so `GCS`'s `\n` works); empty lines are dropped.
- A line that ends with `,<XML>,` (for example `GSI,<XML>,`) opens a document for that command. Following lines are collected until the root element closes; the document is parsed with the existing XML parser into `.xml(command:root:)`. A `<Footer>` element, if one ever appears, is tolerated and ignored.
- Any other line goes to `ResponseLineParser` and becomes `.fields`.
- Limits as for UDP: a document open longer than about 10 s or larger than about 4 MB is dropped, and the assembler returns to line mode.
- Text is decoded as the UDP path decodes it today (lossy UTF-8), so both transports hand the display the same thing. Whether the icon glyph bytes then draw correctly is a display question for stage 2 (§7.3), not a framing one.
- **[assumed]** the scanner never puts a push inside another reply's lines. If hardware shows otherwise (§8), the assembler needs to recognize a nested `PSI,<XML>,` header; the design leaves room by keeping the "open document" state per command.

### 4.3 Finding the scanner: `SerialPortFinder`

- Looks up serial ports through IOKit and keeps those whose USB device has Uniden's vendor ID (0x1965). For each: the callout path, the USB product name, the product ID and the serial number. It sends nothing to any device.
- Per-model data (§4.4) says which product IDs are known (0x001A = SDS150 in serial mode). An unknown Uniden product ID is still offered; `MDL` decides the model once connected.
- A USB station connects to: the port in its device settings (`StationDeviceSettings.usbPort`) if set, and only that port (one that isn't present means "not plugged in": `log` fails with the none-found hint, the app waits for it; Plan 8 D1, §13 Q); with no port saved, the only Uniden port present; otherwise it fails with a message that says what to do: none found ("Plug the scanner in and choose Serial Port on its screen."), or several found (pick one in the station's settings). **(designer's call: automatic by default, because the path depends on a serial number that may not be unique)** The CLI can switch the automatic part off (`NOCTULE_NO_USB_DETECTION`, §13 A), and so can the app (§13 W). Until Plan 8 a saved port that wasn't present fell back to the only Uniden port; §13 Q has the change.
- macOS only, like the transport.

### 4.4 Per-model data

`ModelProfile` gains what the code needs to stop assuming an SDS200: **(designer's call on the exact fields)**

- `hasNetworkAudio` (true only for the SDS200).
- `supportsRemoteRestart` (`MSM,1`; true only for the SDS200).
- `supportsChargeStatus` (`GCS`; true for the SDS150 per **[spec]**).
- `usbProductIDs`.
- `pushKeepAlive` (as built, §13 O): the command that keeps a `PSI` subscription pushing and how often, `KAL` every 60 s for the SDS150, none for every other model.

`protocolVerifiedOnHardware` for the SDS150 becomes true when the §8 checks have passed, not before. (It became true on 2026-11-12, by the owner's ruling: §8.)

### 4.5 Stations and the runner

- `Station.validate()` already requires a host only for network stations. A USB station needs no host, ports or reconnect wait; those fields are ignored for it.
- `StationRunner`'s `makeTransport` closure takes the station's connection (not host and UDP port) and returns the transport; the default builds a `UDPTransport` or, for `usbSerial`, a `SerialTransport` on the port from §4.3.
- **Audio exists only when the station's transport is `network` and the model has network audio.** Otherwise the runner behaves as it does today with save-audio "never": no `AudioSession`, no cooldown wait before the first command, no cooldown record read or written, no recordings. Hit detection and the hit log are unchanged. The station's save-audio rule is kept in the file but has no effect.
- **When the port disappears mid-run** (cable pulled, flat battery, a switch to mass storage; routine for a handheld) the runner, not the app, owns what happens next, so `noctule log` and the app behave the same. Open hits are closed and logged, the runner reports "scanner disconnected" with the §4.3 hint (as built, only when the port is gone; §13 N), and then it **waits for the scanner and resumes by itself (owner)**: it watches for the station's port (§4.3 rules) to reappear, reopens it, sends one `MDL`, and if the model answers as before, runs the normal start (`PSI` subscription and so on). While it waits it sends nothing, since there is nothing to send to. A stop during the wait ends it at once: `noctule log` exits 128 + signo on a signal, or 0 when `--seconds` runs out. This is built here in stage 1, and the app uses it in stage 2. If hardware check 4 (§8) shows that reopening the port upsets the scanner, automatic resume is switched off until the cause is understood. As built, a connection that never delivered a push is not resumed, and each appearance of the port gets a bounded number of probes (§13 F, H).
- **The push keep-alive** (as built, §13 O): both of a USB station's subscriptions, at start and at each resume, pass the model's `pushKeepAlive`; a network station never does.
- Identity for "one session per scanner": for a USB station the address is the resolved port path, so two stations on the same port can't both be open, as two stations on one host can't today. As built (§13 AA), it is the saved port, not the resolved one, and an automatic station conflicts with every USB station.
- As built in Plan 8 (§13 V): a USB subscription that has pushed and then stops, port still there, is ended and replaced through the bounded resume.

### 4.6 Rules that don't change

- One action sends at most one state-changing command and never resends it, even though a USB link should lose far less than UDP's 1 in 12 **[assumed]**. A timeout is still answered by a re-read, not a resend.
- Every subscription ends with `PSI,0` on every exit path.
- Model-specific facts live in per-model data, not branches.

## 5. Command line (stage 1)

**(designer's call on the option names)**

- `--serial [PATH]` on `info`, `status`, `display`, `watch`: talk to a USB scanner; with no path, the one found by §4.3. `--serial` with `--host` is a usage error (exit 2, nothing sent).
- **Which scanner a command talks to is decided by the flag alone.** Without `--serial`, every command targets the network scanner exactly as today, whatever the config file holds. `config/dev-scanner.env` may set `SCANNER_SERIAL` to a path; it is read only when `--serial` is given with no path, and when it is absent or `auto` the finder of §4.3 is used. With `--serial`, the file's `SCANNER_HOST` is not required, so a serial-only file is valid. `NOCTULE_HARDWARE_TESTS=1` talks only to the network scanner; `NOCTULE_SDS150_HARDWARE_TESTS=1` talks only to the serial one. The `.example` template gains the key. As built, `NOCTULE_NO_USB_DETECTION` turns the finding off: a bare `--serial` then finds nothing and `SCANNER_SERIAL` isn't read (§13 A).
- `noctule ports`: lists the Uniden serial ports found (path, product name, known model). Sends nothing. With none, it prints the serial-mode hint.
- `info` prints a battery line (`GCS`) when the model supports it. (Its form, and what happens without an answer: §13 I.)
- `station add --name N --usb [--serial-port PATH]` creates a USB station. `station list` shows `USB` where a network station shows its host.
- `log` runs a USB station: status pushes, hits, the hit log, and hit lines with no file part. It prints one `log: no audio over USB` line at start. `--save-audio`, `--recordings`, `--reconnect-cooldown`, `--cooldown-seconds` and `--cooldown-store` are accepted and have no effect on a USB station. (As built, `log` never took `--save-audio` or `--reconnect-cooldown`, which belong to `station add`; what it prints and how it exits when the scanner goes away, and the one cooldown flag still refused: §13 J.)
- `listen` and `restart` refuse a USB scanner with a one-line reason and exit 2, sending nothing.
- As built (§13 O), `watch --serial` and `log` on a USB station send the model's keep-alive (`KAL` every 60 s on the SDS150) while subscribed; the test-only `NOCTULE_TEST_KEEPALIVE_SECONDS` shortens the interval for runs against the mock.
- Signals behave as today (`PSI,0` before exit; 130/143/129).

## 6. The mock (stage 1)

- `noctule-mock-scanner --model sds150 --serial` starts an SDS150 personality on a pseudo-terminal and prints `serial-port=/dev/ttysNNN`; the CLI and tests open that path as if it were the USB port. It starts no UDP or RTSP servers and has no reconnect hazard.
- The command handling is the existing control core behind a byte-stream front end, with the SDS150's differences as personality data: `MDL,SDS150` (`--mdl-name SDS150GBT` for the **[spec]** form), firmware string, `VOL`/`SQL` 0–15 with out-of-range rejected, `GSI` without a `<Footer>`, `GCS` terminated by `\n`, the existing scenarios and menu tree.
- **Assumptions, not hardware**, to be listed in the mock's type comment as today: the `VOL`/`SQL` rejection form, every menu behaviour (copied from the SDS200 mock), `GCS` values, and `MSM,1` answered `MSM,NG` (the client must never send it; a test asserts the mock never received one).
- **Assumption, not hardware (named by the Plan 8 whole-branch review): the SDS150 keeps sending `PSI` pushes while it is in a menu**, as the SDS200 does (seen on its hardware, protocol notes §4.2) and as the mock does for both models (`MockControlServer` pushes the menu document); the SDS150's menu has never been entered over serial. The app's Mac-style menu, the stall warning and the resubscribe rule (§4.5) rest on it. If it is wrong: 3 s into every menu the runner warns of a stall, and 60 s in (the keep-alive interval) it replaces the subscription (`subscribing again`: `PSI,0`, the port closed and reopened a second later, `MDL`, `VER`, `PSI`), dropping the Mac-style menu for that second; if the fresh `PSI` yields one push and then silence, the cycle repeats about once a minute for as long as the scanner sits in a menu, and whether the reopen or the fresh `PSI` leaves the menu is unknown too. Hardware items 6 and 11 of Plan 8 Task 12 watch for `subscribing again` in a menu; if it shows, the fix is one read-only `GSI` before the replacement, skipping it while the scanner reports `Mode="Menu tree"`.
- As built (§13 O): the SDS150 personality stops pushing 183 s (on the mock's clock) after the `PSI` or the latest `KAL`, the subscription staying; `KAL` gets no reply; `--push-lifetime S` shortens the 183 s. **Assumptions, not hardware:** that every `KAL` restarts the full count (the real unit went on pushing for an hour with `KAL` every 60 s, check 15; the exact rule inside it was not measured), that no other command does, that a `KAL` after the pushes stopped starts them again, and that `KAL` with no subscription does nothing (the last three never tried).
- As built in Plan 8: `--kal-after-expiry ignored` (`MockPersonality.keepAliveRevivesStoppedPushes`) makes a `KAL` after the pushes stopped do nothing, the pessimistic answer to §13 P, so only a new `PSI` starts them again (default `restarts`). Between a trunk-mode scenario's transmissions the SDS150 personality idles as the hardware did, a conventional scan (`MockPersonality.idleForm`): three fictional channels, one per scenario second, each with its frequency and `Sig="0"`. Its idle `STS` carries three icon glyph bytes (0x80, 0x81, 0x8D; `displayGlyphBytes`) over the first three columns of the first line. **Assumptions, not hardware:** the idle channels and their step, the idle `STS` (still the SDS200 mock's screen), and which glyph bytes the SDS150 uses and that each takes one column.
- Faults: the existing `drop-reply` and `drop-request`, plus `unplug=N` (the pseudo-terminal closes after N s, as pulling the cable does) and `split-writes` (replies are written a few bytes at a time, to exercise the assembler).
- In Swift tests the mock is available as a library type on a pseudo-terminal, driven on `MockClock` like `MockSDS200`.

## 7. The app (stage 2)

Built in Plan 8 (`docs/specs/2026-11-12-plan-8-sds150-app.md`) and tested against the mock (unit tests on `MockSerialScanner`, and the built app on `noctule-mock-scanner --model sds150 --serial` in `AppLifecycleIntegrationTests`); run on the SDS150 by the owner on 2026-11-13 (§8). The app no longer refuses a USB station (§13 G). The design bullets below stand; "As built" says where the build differs or adds.

**As built, the session** (`StationSession+USB.swift`; §13 S, Z): a USB station's start reads its device settings, runs the registry's scanner check and takes the station lock, opens the hit log, and never touches the cooldown store. While its port isn't there the phase is `.waitingForScanner(hint:)`, polling `SessionEnvironment.portPollInterval` (1 s) and opening nothing, also when the window opens with the scanner unplugged; then it runs the same `StationRunner` as `noctule log`, with `SessionEnvironment.serialPorts` (§13 W) as the factory's listing. On a disconnect the runner will resume from, the session drops queued keys, pending level changes and the menu, stops its display and battery loops, and goes back to `.waitingForScanner`; one it won't resume from is `.noAnswer(hint)`. A busy port is `.noAnswer(busyPortMessage)`, a scanner silent on its port `.noAnswer(noAnswerUSBMessage(port:))`, any other failure `.noAnswer(usbFailureMessage(_:))` (the error named: `The scanner refused MDL.`, …); none is retried after a wake (§13 Z). `hasAudio` is false: no audio tap, no playback. `restartScanner()` refuses (`Restart isn't supported over USB.`). Menus use the same `MenuModel` as a network station, so while the scanner is in a menu on its own panel the session sends `GSI` and `MSI` about every two seconds with no action in the app (the menu refresh; both read-only), from the moment the window opens if the scanner is already in one.

### 7.1 Adding and editing a station

- The station editor's Connection picker enables "USB". Choosing it replaces the host, ports and Reconnect wait fields with the scanner found (product name and port) or the §4.3 hint, and a port picker only when more than one is present.
- Test Connection sends `MDL` and `VER` through the serial transport and shows model and firmware, as it does for a network station.
- As built (`StationEditorModel`, `StationEditorView`, `StationText.usbStatusText`; §13 X): the Scanner row reads `SessionRegistry.serialPorts` once a second and opens nothing; a saved port that isn't found reads `<path> isn't connected.` plus the hint; the Port picker (Automatic, then each port) also shows when a port is saved, so it can be set back to Automatic; nothing is saved as the port unless the user picks one; the port is written before the station, and a changed port replaces an open session (`SessionRegistry.deviceSettingsChanged`). Test Connection is refused, with nothing opened, while the station's own window holds the scanner (`Disconnect <name> first: its window is using the scanner.`), and always closes the port.

### 7.2 The station window

- Both views work as today from the same `STS`, `GSI` and pushes. Menus use the same `MenuModel`.
- A station without audio shows no Listen control, app volume, audio banner, Reconnect, or Restart scanner. The status bar says "No audio over USB" where the audio indicator is. **(designer's call)**
- Volume and squelch controls use the model's 0–15 ranges.
- The status bar shows the battery (percent, charging or not) from `GCS`, read about once a minute. **(designer's call)**
- When the port disappears (cable pulled, scanner off, scanner switched to mass storage) the window shows a banner with the §4.3 hint and says it is waiting for the scanner. When the port reappears the session resumes by itself (§4.5) and the banner goes away. No cooldown applies. **(owner)**
- **The user can always leave while it waits (owner).** The banner carries a Stations button that does what the status bar's Disconnect does today: it ends the wait, closes the window, releases the session and opens the station picker. The status bar's own Stations and Disconnect buttons, ⌘W and Quit all work during the wait too, and none of them is held up by it.
- Sleep, wake, quit and window close keep today's guarantees, minus everything about RTSP: `PSI,0`, then the port is closed.
- The hit-log window works unchanged; playback and file columns are empty for a USB station's hits.
- As built (`ScannerIndicators`, `MacControlsBar`, `StationContentView`): Listen and the app volume are hidden (`Enablement.showsAudioControls`); the status bar shows `Battery <n>%` (plus `, charging` or `, full`; §13 Y) before `No audio over USB`. The battery comes from one `GCS` at connect and then every `SessionEnvironment.batteryPollInterval` (60 s), only to a model with `supportsChargeStatus`; one missed read keeps the reading, two clear it. The waiting banner is titled `Waiting for the scanner`, with the hint and a Stations button and no Reconnect. **Differs from the bullet above:** a USB station's `.noAnswer` banner (`Can't reach the scanner`) offers Reconnect (never Restart scanner), since nothing else would start it again. The knobs and sliders keep the SDS150's 0–15 through a wait (`StationSession.model`). The Mac-style headline reads `Scanning…` unless `ScannerInfo.isReceiving` (a channel and a signal), since an idle SDS150 names each conventional channel it steps through (§13 P). Sleep is `PSI,0` and the port closed; a wake starts again once, waiting for the port if it isn't back. A start after a wake that fails (a busy port, a silent scanner, anything else) is not retried on the session's backoff (§13 Z): each try would open the port and send `MDL`, and the banner's Reconnect is the way back.

### 7.3 Display and front panel

- The display is the `STS` mirror, unchanged in logic **(owner)**. Stage 2 must check that the SDS150's icon glyph bytes draw as the SDS200's do, and fix the decoding in one shared place if not.
- As built: no decoder change. On the mock (whose glyph bytes are assumed, §6) the bytes decode one character per column and draw as `·`, the highlight mask staying aligned (`DisplayModelTests.glyphBytesKeepTheirColumns`). The read-only hardware suite now requires every `STS` line's text and mask to be the same width and prints only the line count and widths; if the real unit shows a mismatch, the fix (decoding display text one byte per column) changes the decoder the SDS200 uses too and is the owner's to approve.
- The Scanner view keeps the SDS200 panel drawing for the SDS150. The key codes are one table for all SDS models **[spec]**, so every key works; only the picture is not the handheld's. **(designer's call; a handheld panel can be its own small spec)**

## 8. Hardware checks that need the owner

## 13. Decisions made during the build

A to P were made while stage 1 was built, Q onward while stage 2 (Plan 8) was built; none of them by the owner yet (except the `KAL` command in O), and each can be overturned. The letters are the build's own (C was replaced by H; there is no E). Q to Y are the Plan 8 table's D1 to D9, which the owner approved as the plan's assumptions on 2026-11-12 without ruling on each.

- **A. A USB detection kill-switch for the CLI. (designer's call during the build)** `NOCTULE_NO_USB_DETECTION`, set to any non-empty value, makes `noctule` find no USB ports anywhere: `noctule ports` prints the none-found text, a bare `--serial` finds nothing and `SCANNER_SERIAL` is not read, and the transport factory `log` builds for a USB station gets an empty port listing. With it set, `noctule` opens a serial port only when its path is given on the command line or saved in the station being run. A second, test-only variable, `NOCTULE_TEST_SERIAL_PORTS` (colon-separated paths), replaces the system's port listing with a decoy, so a build that ignored the kill-switch would still not find the real scanner (`USBDetection`, in `NoctuleCLICore` then; since Plan 8 in `NoctuleStore`, shared with the app, which follows the same switch, §13 W). Why: a USB station with no saved port uses the only Uniden port detected (§4.3), and so, until Plan 8 (§13 Q), did one whose saved port was missing; on the development Mac that is the owner's real scanner. Agents and tests always set the kill-switch.
- **B. `StationTransportFactory` takes `makeNetworkTransport:`. (designer's call during the build)** So tests and the app can hand in their own network transport; the app passes `SessionEnvironment.makeTransport`, which is unchanged. Why: the factory now builds both kinds of transport, and the network side had to stay injectable as it was.
- **D. Exclusive use of the port is two locks. (designer's call during the build)** `TIOCEXCL`, plus a non-blocking `flock`. Only `EWOULDBLOCK` from `flock` means busy; any other `flock` failure is ignored and `TIOCEXCL` alone holds the port. Why: a pseudo-terminal ignores `TIOCEXCL` for a non-root opener on macOS, so the mock's port needs the `flock`; and an unsupported `flock` on the real device node (never tried) must not make the scanner unopenable. Changes §4.1.
- **F. No automatic resume after a connection that never delivered a push. (designer's call during the build)** The runner emits `.disconnected` once, warns `the scanner isn't sending status updates; not reconnecting by itself`, and idles until `stop()`. Why: a scanner that refuses `PSI` would otherwise get an open, `MDL`, `VER`, `PSI`, close cycle about once a second, a command loop against hardware. The cost: a scanner unplugged within the first push interval of a connection has to be started again by hand. Changes §4.5.
- **G. The app refused a USB station until Plan 8. (designer's call during the build; ended by Plan 8)** `StationSession.start()` ended at once for a station that wasn't a network station, with `USB stations aren't supported in the app yet. Use noctule log in Terminal.`, before the address check, the lock, the cooldown gate and the runner. Why: stage 2 wasn't built, and a USB station reaching the runner from the app would have used the real port listing. Plan 8 removed the refusal (`notNetworkMessage` is gone): the app runs a USB station (§7, §13 S), with the port listing of §13 W. Only a Bluetooth station, and a USB station on iOS, still end at once (`This kind of connection isn't supported on this device yet.`), and `restartScanner()` still refuses anything but a network station.
- **H. Bounded probes while a USB station waits. (designer's call during the build; replaced an earlier reading, C, that allowed one `MDL` per poll)** A scanner that answers as a different model is not probed again until its port has disappeared (a poll at which the station's port doesn't resolve to that path). An unanswered `MDL`, or a failure after it, is retried at most 3 times per appearance; then the runner warns `the scanner isn't answering; unplug it and plug it in again` and probes no more until the port disappears. A busy port (nothing sent) is tried again every poll. A port unplugged and plugged in again between two polls keeps its record. Why: every probe opens the port, which toggles its control lines on hardware whose reaction is unknown, so nothing may probe once per poll for as long as a port stays plugged in. Since the final review, a probe that found the same scanner but couldn't write its `PSI` whole ends the probing of that appearance at once, with the same warning: part of the `PSI` may have reached the scanner, and another probe would send a second one. Changes §4.5.
- **I. The `info` battery line is `battery: 100% (full)`. (designer's call during the build)** Lowercase like the other `info` lines. `GCS` is sent once, and only to a model whose profile has `supportsChargeStatus`; an unanswered or unreadable reply prints `warning: no battery status (<reason>)` and `info` still exits 0. The firmware line shows the version without `Version `, as for the network scanner. Why: a battery reading is extra, not a reason for `info` to fail. Changes §5.
- **J. What `noctule log` does when a USB scanner goes away. (designer's call during the build)** It prints `log: scanner disconnected. <hint>`; then `log: waiting for the scanner…` only when the runner will wait and resume (`StationRunner.willResume`); when it won't (F), `log` prints the runner's warning, stops the runner and exits 1. A USB station whose port isn't there, or is busy, when `log` starts fails at once (exit 1) and doesn't wait. `log --cooldown-seconds` without a private `--cooldown-store` is still refused (exit 2) for a USB station too, since that check comes before the station is read; `--recordings`, and `--cooldown-seconds` with a private store, are accepted with no effect. Why: a `log` that waited for a resume that will never come would look alive and log nothing. Changes §5.
- **K. The opt-in SDS150 tests have two gates and an interlock. (designer's call during the build)** `SDS150HardwareTests`' read-only suite needs `NOCTULE_SDS150_HARDWARE_TESTS=1`; its push suite needs that and `NOCTULE_SDS150_PUSH_TEST=1`; both are skipped while `NOCTULE_NO_USB_DETECTION` is set, decided from the environment before any port is resolved or opened. The same checks run against the mock by default, which pins exactly what each sends. Why: agents export the kill-switch, so no agent shell can run them by accident, and what they send is known before the owner runs them. Changes §8's last line.
- **L. `StationTransportFactory` has no default port listing. (designer's call during the build, from the final review)** Its `ports` is required. `StationRunner`'s default factory and `StationSession` pass `FixedSerialPortListing.empty` (in `NoctuleKit`, beside `SerialPortListing`; the CLI's kill-switch uses it too), so a USB station run without the shell's listing opens its saved port or nothing. Only the `noctule` shell passes the system's listing (`IOKitSerialPortFinder`), through `USBDetection`; the opt-in SDS150 hardware tests build it too. (Since Plan 8 a USB station's session passes `SessionEnvironment.serialPorts`, empty by default; only the app's `AppDelegate` fills it with the system's listing, and `applyingOverrides` then applies §13 W's rule.) Why: the IOKit listing was the default one layer below the CLI's kill-switch, so a future caller that built a runner for a USB station without a factory would have found the real scanner without a word. Changes §4.3.
- **M. A requested close waits, bounded, for the output to leave. (designer's call during the build, from the final review)** Before `SerialTransport` closes the port on `close()`, its reader thread reads `TIOCOUTQ` every 5 ms until the output queue is empty, the request fails, or 250 ms have passed, then waits 20 ms more (the queue doesn't see what the USB driver holds). There is no wait after the device went away (the descriptor is already closed), never `tcdrain`, and `O_NONBLOCK` is never cleared: both could block without bound on a device that stopped reading. Why: the last close of a non-blocking tty discards queued output, so the `PSI,0` written just before every close could be lost on the real port; the mock's pty, which keeps its own end open, never showed it (LESSONS.md 2026-11-11). A close takes at most about 0.3 s. Whether that is enough on the SDS150 is what §8's quiet-port check shows. Changes §4.1.
- **N. The disconnect hint depends on whether the port is still there. (designer's call during the build, from the final review)** When a USB station's push stream ends, `.disconnected` carries `Plug the scanner in and choose Serial Port on its screen.` only if the station's port no longer resolves; if it still does (the scanner refused `PSI`, or the subscription was ended), it carries `The scanner is connected but isn't sending status updates.` (`SerialPort.notSendingUpdatesHint`), which `noctule log` prints as `log: scanner disconnected. <hint>`. Why: telling the user to plug in a scanner that is plugged in sends them the wrong way. The port is looked up right after the link ended; if the SDS150's device node outlives the end of the stream by a moment, an unplug could get the second hint (unmeasured; §8 check 11). Changes §4.5.
- **O. A keep-alive for `PSI` subscriptions on the SDS150: `KAL` every 60 s. (owner-approved command, 2026-11-12; the rest the designer's call during the build)** Seen on hardware (§8 check 6, three timed runs): the SDS150 stops pushing 183 s after the `PSI`, the port open and the scanner answering. Uniden's spec lists `KAL` ("Keep Alive", no reply, no timeout given); the owner approved sending it over USB ("I am fine with adding KAL into the usb channel interfacing") and suspects an internal watchdog that `KAL` resets. Built: `ModelProfile.pushKeepAlive` (`KAL` every 60 s for the SDS150, three chances inside 183 s; none for any other model); `ScannerClient.startPush(interval:keepAlive:)` writes it while that push is the active one, the first no sooner than one interval after the `PSI` and each next no sooner than one interval after the previous write (so never two closer than an interval; a late wake is late and never catches up), with no reply awaited, never after that push's `PSI,0` or once `disconnect()` has returned (every stop awaits a keep-alive already on its way before it writes `PSI,0` or closes), and never again after a write that failed; `PushKeepAlive.forSubscription` passes it only over a serial link and only for a model that has one, so the network path and the SDS200 are unchanged; `StationRunner` (start and each resume) and `noctule watch --serial` use it; `NOCTULE_TEST_KEEPALIVE_SECONDS` (tests only) shortens the interval. A reply to `KAL`, should one come, is an unmatched line the client drops. The mock's SDS150 stops pushing 183 s after the `PSI` or the latest `KAL`, and `--push-lifetime` shortens that for tests. **Run on hardware, 2026-11-12 (check 15):** with `KAL` every 60 s the pushes went on for 240 s, 300 s and an hour of `log`, so for as long as `KAL`s come, and the unit sent nothing back for a `KAL` (seen in the 240 s check, the one that reports such lines). The first three runs were on the build with a fixed 60 s grid; the 240 s check passed again on the merged build with the spacing rule above. **Still assumed:** the exact rule inside the scanner (the mock restarts the full 183 s at each `KAL`), that a `KAL` sent after the pushes have stopped starts them again (P below), that no other command resets it, and that another interval would do (only 60 s was tried). `protocolVerifiedOnHardware` became true for the SDS150 on 2026-11-12 by the owner's ruling, with check 12, a trunked hit and check 7 (Plan 8) not run. Had `KAL` failed, the fallback was a fresh `PSI` before the 183 s are up, which the hardware showed restarts the pushes. **Follow-up, not built:** a `KAL` write that fails ends the keep-alive silently (by design: never retried), so the user only learns of it three minutes later from `scanner stopped sending updates`, and a USB station doesn't resubscribe after a stall; a warning event at the failed write would say why (QA M3). (Built in Plan 8: the warning, §13 U, and the resubscribe, §13 V.) Changes §2, §3.2, §4.4, §4.5, §5, §6 and §8.

- **P. What the second whole-branch review left open (2026-11-12, `f6a0fed..532bdbd`; nothing Critical). (for the owner and Plan 8)**
  - **A pause longer than the push lifetime.** If the Mac sleeps under `noctule log` (or the process is stopped) for more than 183 s while the SDS150 stays connected, the scanner stops pushing. On wake the keep-alive writes one `KAL` and goes on every minute; the runner warns `scanner stopped sending updates` once and does nothing else. Whether a `KAL` starts stopped pushes again is the mock's assumption, never tried on hardware (§8 check 16); a new `PSI` does, as seen. If it doesn't, `log` runs on and logs nothing. The fix to rule on, together with O's silent failed `KAL` write since it is the same hole: when a USB connection that had delivered pushes has been stalled for more than one keep-alive interval with its port still there, end it as a push end is ended (`PSI,0`, close) and let the bounded resume send a fresh `PSI`.
