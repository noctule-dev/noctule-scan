# Noctule Scan — agent instructions

Noctule Scan is a macOS app (iPad and iPhone later) and a command-line tool, `noctule`, for controlling, listening to, and logging Uniden SDS-series radio scanners:

- the **SDS200** over the network (UDP control, RTSP audio);
- the **SDS150** over USB serial (control and hit logging, a battery reading, no audio over USB; Plans 7 and 8), kept pushing by `KAL` every 60 s;
- the **SDS100** over USB serial, on the SDS150's stack (no battery reading; Plan 17), kept pushing by its own `PSI,<ms>` written again every 60 s;
- **line-in audio** for a USB station: the scanner's headphone jack by a cable into a Mac audio input, for recordings, the hit log, playback, Listen and a level meter (Plans 18 and 19);
- the **Favorites quick keys** on all three (Plan 20): `noctule quick-keys` prints them read-only, and the app's Quick Keys pop-over turns them on and off.

All three are subscribed at 100 ms and their screen read at each step of a scan (`ModelProfile.pushInterval`, `displayRefreshInterval`).

This file is for any contributor's agent. "Your scanner" is a real scanner on the desk of the person you work for; it is real hardware they rely on, and the rules below protect it. A maintainer may keep rules about their own units in a git-ignored `AGENTS.local.md` (read through a git-ignored `CLAUDE.local.md`); those add to these and never relax a rule here unless they say so for their own setup. In the specs, "the owner" means the maintainer, and dated hardware results were on the maintainer's units (`docs/specs/README.md`).

## Working rules

- **Specs and plans** go in `docs/specs/`, named `YYYY-MM-DD-<topic>.md`.
- **Update `LESSONS.md`** whenever something surprises you, costs time, or changes how we work: a dated entry with what happened and what to do. Do it during the work, not at the end.
- **Language:** Swift and SwiftUI. Keep scanner protocol, transports, stations, logging, and storage in shared code with no Mac-only UI dependencies, so iPad and iPhone can reuse them.
- **Model-specific knowledge** (commands, key maps, display layouts) lives in per-model data (`ModelProfile`), not scattered branches.
- **No personal values in code or tracked files.** Hosts, IP addresses, serial port paths and credentials go in git-ignored `config/*.env`. Commit only `*.env.example` templates.
- **No real radio traffic in tracked files:** no real system, site, or channel names, frequencies, unit IDs, or NAC/Sys ID/WACN values, even in fixtures and spec samples. Sanitize captures to fictional values of the same shape. You may keep a deny-list in the git-ignored `config/real-names.txt` (template `config/real-names.txt.example`); `RealNamesTests` checks every tracked text file against it when it exists, and skips when it doesn't.
- **Uniden manuals** (`docs/uniden/*.pdf`) are copyrighted and git-ignored. Don't commit them. `docs/uniden/README.md` says where to get them.
- **Third-party knowledge:** the `sds200` Python library (MIT, © Steven Boyd) is our main protocol reference. Write our own code; if anything is ever ported, keep its license notice and credit it in `ACKNOWLEDGMENTS.md`.
- **Branding:** no Uniden logos or trademarks in the app's branding. The Noctule name and art are not licensed with the code (`TRADEMARKS.md`); the official art is not in this repository (see Branding below).
- **Every commit is signed off** (`git commit -s`, which adds `Signed-off-by:` matching the author): the project uses the DCO (`CONTRIBUTING.md`), and CI fails a pull request with a commit that lacks it (`scripts/check-dco.sh`).
- **Every new source file** (`.swift`, `.sh`, `.py`, `.yml`) starts with the two-line SPDX notice, after a `#!` or `// swift-tools-version` line if any, in that language's comment form (`# ` for shell, Python and YAML); `RepositoryHygieneTests` fails without it:

## Your scanner: rules for real hardware

**Test every feature against the mock first, and a real scanner second** (see the mock below). A run against a real scanner, and each app launch against one, is the call of the person you work for, each time. The rules apply to every route: the command line, tests, scripts, the app, and QA mutations.

### Every model

- **Probe read-only** by default: `MDL`, `VER`, `VOL`/`SQL` with no argument, `GSI`, `STS`, `MSI` (describes the current menu screen; outside a menu it answers a `TypeError` screen), the quick-key reads below, RTSP `DESCRIBE` on the SDS200, and on a USB handheld `GCS` (read-only by Uniden's spec; one, never a loop). Ask the person you work for before sending anything that changes scanner state.
- **State-changing commands** (`KEY` presses, `MSV`, a `VOL` or `SQL` value, a quick-key set) need their go-ahead each time, never in a loop, and never from a test that isn't marked as changing state. An `MSV` can run an action or save a value; `KEY,M,P` opens a menu and moves around in it.
- **One action sends at most one state-changing command, and it is never resent**, not even after a timeout: a lost request looks like a lost reply (about 1 UDP command in 12 goes unanswered on the SDS200), so only a re-read (`GSI`, `MSI`) says whether it took effect (LESSONS.md 2026-11-10). The app's menu code does this (`MenuModel`); any new caller must too. The same holds over USB.
- **Quick keys** (quick-keys design §5.6; the same on all three models): the reads, `GLT` (`GLT,FL`, `GLT,SYS,<i>`, `GLT,DEPT,<i>`, `GLT,SITE,<i>`) and `FQK`, `SQK,<list key>` and `DQK,<list key>,<system key>` with no values, are read-only (`noctule quick-keys` sends `MDL` and only these). **A set (`FQK`, `SQK` or `DQK` with 100 values) changes scanner state**: the go-ahead each time, one per action, never resent, not even after a timeout; only a re-read says whether it took effect. The product sends a set only from a user's click in the Quick Keys pop-over (`QuickKeysModel.toggle`), never on its own, and **one click sends several reads and at most one set**: a tile's click one `FQK` set; a system's, department's or site's click first up to five or six read-only `GLT` reads proving its address (`proveAddress`; if they don't prove it, or one goes unanswered, nothing is set), then one `SQK` or `DQK` set; the set names only the clicked key, 0 everywhere else, and is followed by a re-read of that scope. Tests never send a set to real hardware, and no hardware test sends one.
- **Never send guessed or undocumented commands** (an `ESN` query, for one). The one exception is **`MSM,1`** (remote restart) to an **SDS200 over the network**, sent only when the person you work for has explicitly confirmed that restart, never automatically and never in a loop (`noctule restart`; the opt-in `NOCTULE_RESTART_HARDWARE_TEST=1` test sends it, run only when they ask). **Never `MSM,1` over USB** (it isn't in Uniden's serial spec; `noctule restart` refuses `--serial`, and the app's Restart refuses a USB station), and **never `POF`** (power off) to any model.
- **`KAL` only from the push keep-alive, and only to a model whose profile has a `KAL` keep-alive** (today the SDS150; `ModelProfile.pushKeepAlive`). `ScannerClient` writes it every 60 s while a `PSI` subscription runs, only over serial (`PushKeepAlive.forSubscription`), never after that subscription's `PSI,0`, never again after a write that failed, and never while another command's reply is pending (it waits for the client's request slot; SDS150 design §13 O, U). Never send it by any other route, or to the SDS200 or the SDS100 (which answers it `ERR`).
- **Always `TEARDOWN` RTSP audio sessions**, in every exit path, including failing tests and interrupted scripts. A leaked session can leave the SDS200's audio dead until a power cycle. If audio wedges, stop and tell the person you work for rather than retrying in a loop.
- **Keep `PSI` pushes tidy:** send `PSI,0` when you're done with a subscription, on every path.
- **The reconnect cooldown** (Plan 5, `docs/specs/2026-11-09-plan-5-stations-cooldown.md`). After an *unclean* RTSP close (a crash or dead lease, a failed connect, a server-closed or dropped connection, an unanswered or non-2xx TEARDOWN, any unanswered request, a connection that never had a session) the next connection always waits the full 120 s. After a *clean* close (a session set up, every TEARDOWN answered 2xx, every request answered, closed by `close()`) it waits the station's own setting, `StationConnection.reconnectCooldownSeconds` (0–120 s, default 120; for `listen`, `--reconnect-cooldown`). **The person you work for sets that value; agents never lower it against a real scanner on their own**, and never pass `--reconnect-cooldown` below 120 against one unless asked. A clean close never hides an unclean one. `--cooldown-seconds` and `NOCTULE_COOLDOWN_SECONDS` are mock-only: they set the full value, and the clean value is clamped to it. **Never shorten the full value against a real scanner**, and never delete the cooldown record to skip a wait.
- **The protocol has no authentication.** Never expose a scanner or any relay to the internet.

### USB handhelds (the SDS150 and the SDS100)

- **Agents `export NOCTULE_NO_USB_DETECTION=1`** (the kill-switch, below) in every shell that runs `noctule`, tests or scripts, and never run a bare `--serial`, or `noctule log` on a USB station, against anything but the mock unless asked for a hardware run. **Pass `--serial` only the mock's path.**
- **Never open, read, write or `stty` a `/dev/cu.usbmodem*` or `/dev/tty.usbmodem*` path yourself.** To look at a real port, use the quiet-port hardware check (below), never `cat` or `screen`.
- In a hardware run you were asked for, pass the radio's explicit path, checked against the registry by product name just before each run (`noctule ports`, which opens nothing, or `ioreg`), and let `MDL` name the expected model before anything else is sent. `PSI`, its keep-alive and `PSI,0` belong to a run you were asked for; always end a subscription with `PSI,0`.
- **What "the only Uniden port" means.** With detection on, a bare `--serial`, `SCANNER_SERIAL=auto`, and a USB station with no saved port all use the only Uniden port found: with two handhelds plugged in, neither (a bare `--serial` prints one line per port and `Pass --serial PATH to choose one.`, exit 2; `log` fails with `More than one Uniden scanner is connected. Choose its port.`; the app waits, showing that hint). So with two plugged in every USB station needs a saved port, and an Automatic USB station conflicts with every other USB station in the app (SDS150 design §13 AA). A station whose saved port is missing never falls back to a found one (§13 Q): `log` fails with the plug-in hint, and the app waits for that port.
- **The port is exclusive:** while `noctule` or the app has it open, another `noctule` on it gets `<path> is in use by another program.` and sends nothing, and so does the app (in the window's banner; not retried after a wake). Find and stop what holds it; don't retry in a loop.
- **A close waits**, at most about 0.3 s, for what was written to leave the Mac (`SerialTransport`; §13 M), so a `PSI,0` written just before the close takes effect.
- **The SDS100's keep-alive is the renewal** (SDS100 design §5.2, §10; `PushKeepAlive(action: .renewSubscription, interval: .seconds(60))`): while a subscription runs, `ScannerClient` writes that subscription's own `PSI,<ms>` again every 60 s on the open port, with no `PSI,0` between, under every rule of `KAL` above (never while a reply is pending; none after that push's `PSI,0`, a stop, a cancel, a disconnect or a newer push; a failed write reported once, never retried), and never over the network. A newer push waits for an older push's renewal whose write has begun, so the scanner never ends on the older rate. A `PSI,NG` once a renewal's write has begun is the renewal's: the push stays (its stop still writes `PSI,0`), its renewals end, and it is reported once as a failed keep-alive (`PushRenewalRefused`).
- **`GCS`** is sent by the product only to a model whose profile has `supportsChargeStatus` (the SDS150): never to the SDS100, where it gave no reading, nor over the network.

### Your saved settings can point at real hardware

The command line and the app share `~/Library/Application Support/NoctuleScan/` (`stations.json`, `device.json`, `app.json`, the hit logs), `~/Music/Noctule Scan/` and the RTSP cooldown record. **The kill-switch does not cover a port saved in a station.**

- **Agents always pass `--settings-dir` (a temporary directory) to `noctule station`, `log`, `hits` and `listen --station`.** Without it: `log` opens a USB station's saved port whenever it is there, kill-switch or not; a bare `noctule log` runs the last station `log` ran (and `log` makes the station it runs the last one); `listen --station <name>` on a real network station opens a real RTSP session, and on a line-in station only the kill-switch stands between it and the room; `noctule hits` prints real names.
- **The app, launched normally** (no `NOCTULE_SETTINGS_DIR`, no kill-switch), reads the real settings, uses the system's port listing, and at launch opens the last connected station's window and starts its session by itself: for a USB station `MDL`, `VER`, `PSI,100`, `STS`, the model's keep-alive and, on an SDS150, `GCS`; whenever the scanner is in a menu on its own panel, `GSI` and `MSI` about every two seconds (both read-only). **Agents never launch the app without `NOCTULE_SETTINGS_DIR` pointing at a temporary directory whose only stations are mocks, and `NOCTULE_NO_USB_DETECTION=1`** (see the Mac app below).

## What the hardware does

Facts from real units (the specs cited have the measurements). Anything not listed here or in the specs is unverified; the mock's assumptions are listed in its type comments.

- **The SDS200 is fragile.** A quick RTSP reconnect, a leaked session, or a bad request can leave its audio (or its whole network stack) dead until it is power-cycled. An RTSP connection opened within about 120 s of the previous close can wedge its audio server (the reconnect hazard). Only a power cycle is proven to clear a wedge; that `MSM,1` does is unverified (protocol notes §8.8), and `MSM,1` only helps while UDP control still answers. About 1 UDP command in 12 goes unanswered (remote menus design §4.5).
- **The SDS150's `PSI` pushes stop 183 s after the subscription starts**, port still open and the subscription staying, so without a keep-alive `watch` exits 1 and `log` warns after three minutes (LESSONS.md 2026-11-12). `KAL` every 60 s kept them going for an hour of `log`, with nothing sent back for any `KAL` (SDS150 design §8). Only `KAL` at 60 s was tried. Unverified: whether a late `KAL` (after a pause longer than 183 s, such as a Mac asleep under `log`) starts them again (§13 P), trunked hits, an unprogrammed channel, a terminal program sharing the port, Bluetooth. A subscription that stops pushing is replaced with a fresh `PSI` (§13 V), so hits come back either way.
- **The SDS100's pushes stop about 182–186 s after the subscription starts**, port still open. **`KAL` does nothing there: it answers `ERR`.** The same `PSI` written again every 60 s on the open port kept the pushes going (proven for 240 s at 60 s; SDS100 design §3.3). `GCS` gave no usable reading on firmware 1.26.01 (§3.5). With `PSI,100`, pushes come about every 137 ms. Its read-only commands answer as the SDS150's do. Unchecked on a real unit (design §7): menus, an unplug and replug, a run longer than five minutes, `Battery` in `GSI`, the `STS` line widths, and the hour of `log`.
- **Two handhelds share a USB identity:** vendor ID 0x1965 and **product ID 0x001A on both**; the product name (`SDS150 Serial Port`, `SDS100 Serial Port`) is what tells them apart (`SerialPortInfo.knownModel` reads the product name first, and falls back to the product ID only when exactly one model's `usbProductIDs` holds it, so a 0x001A port with no product name is `unknown model`). **The SDS100 reports no USB serial number**, so macOS names its port from the USB location (`/dev/cu.usbmodem<location>1`): **its path follows the socket**, and moving the cable to another socket or hub changes it, so a saved port must be picked again. The SDS150's comes from its placeholder serial number and stays put. No command gives either radio's serial number, so two radios of one model can't be told apart (SDS100 design §3.1, §8).
- **A handheld doesn't exist on USB until Serial Port is chosen on its screen** (the other choice, mass storage, is a different USB device). It has no audio over USB.
- **Serial `GLT` replies come in pages** on both handhelds: every document ends with `<Footer No="n" EOT="0|1"/>`, the pages paged by size (6–13 elements a page seen), `EOT="1"` on the last; they must be put together before reading (protocol notes §5b, quick-keys design §3.1). **Every Favorites `Index` is unique** across lists, systems, departments and sites. `GSI` and pushes name the scanning list with `Q_Key="0"`, the wrong key, so matching by quick key fails. Quick-key reads answer the 100 values only (0 none, 1 off, 2 on); an `FQK` or `SQK` set takes about 0.8 s to answer. `FQK` and `DQK` sets carrying zeros have never run on hardware (quick-keys design §7).
- **A conventional transmission** (no talkgroup) has its frequency, modulation and tone as attributes of `ConvFrequency` (`Freq`, `Mod`, `SAD`, with `TGID="TGID None"` and `U_Id="UID None"` placeholders), no `Site` or `SiteFrequency`, and `Mode="Scan Mode" V_Screen="conventional_scan"`, on both the SDS150 and the SDS200. An SDS150 between transmissions names each conventional channel it steps through, with `Sig="0"`, so receiving means a channel and `Sig` above 0 (`ScannerInfo.isReceiving`).
- On the SDS150 `GCS` on USB power answers `CST=8`, a state code Uniden's spec doesn't list. Its `MSI` leaves out Manage Full Database's Review Avoids, which only the Scanner view reaches.
- **A line-in rig** measured an idle floor of -52 dBFS RMS and a peak of -3.4 dBFS at volume 5 on a mono input (line-in design §3a); nothing else about the jack's level curve is measured.

## The mock scanner (use it first)

`noctule-mock-scanner` imitates the hardware closely enough to find the mistakes above on your Mac, the reconnect hazard included. Its logic and argument parsing are in the `NoctuleMockScanner` library; `Sources/noctule-mock-scanner/main.swift` is its I/O shell. **What it does that no real unit was seen to do is listed as "Assumptions, not hardware" in the type comments of `MockMenu`, `MockPersonality`, `MockSerialScanner` and `MockFavorites`**: read them before trusting a mock behaviour.

### The network mock (an SDS200)

- `swift run noctule-mock-scanner` starts it on 127.0.0.1 and prints `udp-port=P` and `rtsp-port=P` (ephemeral unless you pass `--udp-port`/`--rtsp-port`). Point the CLI at it: `noctule info --host 127.0.0.1 --port <udp>`, `noctule listen --host 127.0.0.1 --port <udp> --rtsp-port <rtsp> --cooldown-store /tmp/mock-cooldown.json`. Ctrl-C stops it and prints `leaked-sessions=N` (RTSP sessions that never got a TEARDOWN; anything but 0 is a bug). `--verbose` logs every control command and RTSP request to stderr.
- It speaks UDP control (`MDL`, `VER`, `VOL`/`SQL`, `GSI`, `STS`, `KEY`, `PSI`, `MSI`, `MSV`, `MSM,1`, the quick-key commands), streams RTSP/RTP the way firmware 1.26.01 does (25 packets/s of 320-byte PCMU, reply delays of about 0.5 s; `--no-delays` turns them off), and plays a synthetic tone during each transmission of its scenario: `--scenario default` (fictional trunk traffic, one unprogrammed talkgroup), `--scenario weather`, or a JSON file shaped like `Sources/NoctuleMockScanner/Scenarios/default.json`.
- **Menus:** `KEY,M,P` opens a fictional menu tree (`MockMenu.swift`: an on/off list, a number entry, ten name entries, an Analyze screen `MSI` can't describe, a pick-one setting, Settings) that `STS`, `GSI`/`PSI`, `MSI` and `MSV,,<value>` show and drive in the hardware's shapes (remote menus design §4). `MockSDS200` exposes `isInMenu`, `menuPath` and `menuActions` (`toggle <item> <On|Off>`, `set <screen> <value>`, `run <action>`). `powerCycle()` and `MSM,1` leave the menu and restore its values.
- **The reconnect hazard:** an RTSP connection opened within `--cooldown-seconds` (default 120) of the previous close wedges its audio server, until `noctule restart` (`MSM,1`, which silences it for `--reboot-seconds`, default 10) or a restart of the mock (that `MSM,1` clears it is the mock's assumption). `--wedge-mode timeout|refuse` picks what the wedged server does with connections (on loopback `timeout` means the first request gets no answer, since the kernel always completes the TCP handshake; LESSONS.md). `--cooldown-after any|unclean`: `any` (the default, the hardware as measured) or `unclean` (a close by the client after a 2xx TEARDOWN on that connection doesn't start the window, provided every request on it was answered, no TEARDOWN got a non-2xx reply and no reply had a wrong CSeq; a theory for testing the clean-close cooldown, no evidence about the hardware).
- With a shortened mock cooldown, pass the CLI a `--cooldown-seconds` at least as long and a private `--cooldown-store`. To test a station's clean-close wait below the mock's window, run the mock with `--cooldown-after unclean`.

### Faults

- `--fault drop-reply=NAME[:N]` (the next N control commands NAME, e.g. `KEY`, are carried out but get no reply) and `--fault drop-request=NAME[:N]` (logged and ignored); N defaults to 1 and is shared by both (`MockFaults.dropNextReply`, `dropNextRequest`, `dropCount`). They model the lost datagrams. Test-only, no CLI flag: `MockFaults.rejectNext` (a command name) answers the next `dropCount` of them `<NAME>,NG` without carrying them out; `Options.replyDelays[<command>]` holds that UDP command's (or RTSP method's) reply back in real time, the command taking effect at once.
- `--fault stall-psi=N` (pushes stop after N s), `keepalive=454` (the next keepalive fails, once), `drop-audio=N` (RTP stops N s after PLAY), `wedge-audio` (SETUP answers 503 until a reboot), `wedge-control` (when audio wedges, UDP control goes silent too, so only a restart of the mock helps).
- Serial only: `--fault unplug=N[:M]` (the pty closes N s after start, as pulling the cable does; with `:M` a new one appears M s later behind `--serial-link`, which `:M` needs), `--fault unplug-after-psi=N[:M]` (the same, but N counts from the first subscribing `PSI` the mock receives: what a test means by "connected, then the cable goes", whatever the client's start-up took; `MockFaults.unplugCountsFromFirstPSI`) and `--fault split-writes` (every reply written 7 bytes at a time). `stall-psi`, `drop-reply` and `drop-request` work over serial too.

### The serial mock (an SDS150 or an SDS100)

- `swift run noctule-mock-scanner --model sds150 --serial` (or `--model sds100 --serial`) serves a pseudo-terminal instead of UDP and RTSP and prints `serial-port=PATH` (the pty, or with `--serial-link PATH` a symlink to it that stays put across an unplug and replug; a symlink already there is replaced, anything else is an error). Point the CLI at it (`noctule info --serial <path>`) or a station (`station add --usb --serial-port <path>`). Ctrl-C prints `active-subscriptions=N` (`PSI` subscriptions a client left running; anything but 0 is a bug). No audio, RTSP, cooldown or reconnect hazard. `--model sds150|sds100` needs `--serial`; `--serial` refuses `--udp-port`/`--rtsp-port`; `--serial` alone serves the SDS200's answers on a pty. `--mdl-name NAME` reports another model name (e.g. `SDS150GBT`, the form Uniden's spec gives). The scenarios and the menu tree are the network mock's.
- **The SDS150's answers:** `MDL,SDS150`, `VER,Version 1.01.02`, `VOL`/`SQL` 0–15, XML documents as `\r`-separated lines with no `<Footer>` (but `GLT`'s pages), `GCS` ending in `\n`, `MSM,1` answered `MSM,NG` with nothing else happening, conventional transmissions in the hardware's `ConvFrequency` shape (`MockScreens.convFrequency`), and between a trunk scenario's transmissions an idle conventional scan (three fictional channels, one per scenario second, `Sig="0"`; `MockPersonality.idleForm`). **Push lifetime:** pushes stop 183 s (on the mock's clock) after the `PSI`, the subscription staying; every `KAL` restarts the count; `KAL` is logged and never answered. `--push-lifetime S` (serial SDS150 or SDS100 only; positive seconds) shortens it for tests. `--kal-after-expiry ignored` (SDS150 only) makes a `KAL` after the pushes stopped do nothing, the pessimistic answer to SDS150 design §13 P (default `restarts`). Every other model answers `KAL` `ERR`; the network mock has no lifetime.
- **The SDS100's answers** (`MockPersonality.sds100`; SDS100 design §5.4): `MDL,SDS100`, `VER,Version 1.26.01`, `VOL`/`SQL` 0–15, the SDS150's XML form, `KAL` answered `ERR` and restarting nothing, `GCS` answered `ERR`, `MSM,1` answered `MSM,NG`, a trunk idle form between transmissions (`IdleForm.trunkSite`), and four icon glyph bytes on the idle screen. **Push lifetime:** pushes stop 183 s after the latest `PSI` from that client; a `PSI` while subscribed restarts the count and adds no second subscription (`activeSubscribers` stays 1), which is how the renewal keeps it pushing. `--kal-after-expiry` is refused. On the mock a renewal restarts the push timer, so **a test that shortens the renewal keeps it at least twice the push interval** (LESSONS.md 2026-11-16).
- **The headphone jack** (`--line-out PATH`, serial only; line-in design §8, §12): the scanner's headphone output on a Unix-domain stream socket at PATH, printed as `line-out=PATH` and removed on Ctrl-C (a stale socket is replaced, anything else is an error; **a path of 104 bytes or more is refused, so use a short directory of its own**, LESSONS.md 2026-11-17). Interleaved stereo little-endian Float32 at 48 kHz in 20 ms blocks, in real time, **one client at a time** (a second reads end of file); audio made while no client is connected is discarded. Each transmission plays a sine at peak `VOL / 8` (`MockLineOut.peak(forVolume:)`) over -52 dBFS RMS noise, hard-clipped, so `VOL` 8 and up clips; `VOL,n` changes it at once. `--line-out-channel left|right|both` (default `both`) and `--fault line-out-silent` (noise only) need `--line-out`. In tests, `PipeLineInSource` reads the socket in place of a device (`MockSerialScanner(lineOut:)`, `MockLineOut`).

### Favorites quick keys on every mock

Every mock answers `GLT,FL`, `GLT,SYS,<list Index>`, `GLT,DEPT,<system Index>`, `GLT,SITE,<system Index>`, and `FQK`, `SQK,<list key>`, `DQK,<list key>,<system key>` reads and sets (`<CMD>,OK`), from the fictional tree `MockFavorites.default` (quick-keys design §5.2, §10: eight lists on keys spread over the tens, one with none, a list that isn't monitored, unique indexes, a trunked system keyed on its sites, shared keys, an avoided system, and a system whose departments `DQK` reports as 0). Every `GLT` reply is paged with footers (`gltPageSize` elements a page, 4 by default; `MockSDS200.Options.gltPageSize`, `MockSerialScanner(gltPageSize:)`, `--glt-page-size N`), each page its own `GLT,<XML>,` line (a write over serial, a datagram over UDP). `GSI` and pushes carry the wrong `Q_Key="0"`, as the hardware does. `FQK` and `SQK` sets reply after `quickKeySetDelay` (800 ms; zero under `--no-delays`), `DQK` at once. Faults, `rejectNext` and `replyDelays` apply as to any command; tests read and replace the tree with `favorites` and `setFavorites(_:)`.

### In Swift tests

- `MockSDS200` on a `MockClock.stepped()` clock, with short `reconnectCooldown` and `rebootDuration` (and `cooldownAfter: .unclean` to model clean closes); `powerCycle()` and `setFaults(_:)` drive it, and `leakedSessions` should be empty when a well-behaved client is done.
- `MockSerialScanner` (`personality: .sds100` for the SDS100) on a `MockClock.stepped()` clock: open the path its `start()` returns (with `linkPath:`, a symlink that survives `unplug()` and `replug()`). `setFaults(_:)` takes `unplugAfter`, `replugAfter`, `splitWrites` and `pushBeforeStop` (test-only, no CLI flag: one push written just before the next `PSI,0` is handled, so it is on the wire ahead of that `PSI,OK`) besides the shared faults; `receivedCommands`, `activeSubscribers`, `pushesSent`, `volume`, `squelch`, `isInMenu`, `menuPath` and `menuActions` show what happened. Read `receivedCommands` and `activeSubscribers` after `stop()`, which takes in what the client wrote before the port closed (LESSONS.md 2026-11-11); `activeSubscribers` should then be 0.
- **Never let a test find "the only Uniden port" by itself:** on a developer's Mac that may be a real handheld. Pass the mock's path, and give `StationTransportFactory` your own `ports:` listing.

## Line-in audio

A USB station records, plays and meters the scanner's headphone jack through a Mac audio input (line-in design §12). The input is set in the station editor or `station add --audio-input`, and saved in `device.json` (`audioInputDevice`, `audioInputName`, `audioInputChannel`); capture is `NoctuleAudioCapture` (an `AVAudioSinkNode` into `LineInPipeline`: 16-bit 8 kHz mono chunks of 320 samples, levels measured at the device's rate), behind the `LineInSource` protocol in `NoctuleKit`, which `StationRunner` takes as a factory. A line-in station never touches the RTSP cooldown.

- **Agents never open a real audio input.** Never construct `EngineLineInSource.system`, query `CoreAudioInputs`, or call `AVAudioApplication`'s permission request, from a test, a command, a script or a QA mutation: it shows the microphone prompt and records the room. Tests use `FakeLineInSource`, or `PipeLineInSource` on `MockLineOut`. **A QA mutation that removes the kill-switch check is forbidden**: test the selection (`LineInDetection.selection`), never the system factory. A run with a real line-in is the call of the person you work for, each time.
- **Recordings from a real line-in are real radio audio**: never commit them, and delete test recordings after a hardware check.
- **The kill-switch also turns off audio inputs.** With `NOCTULE_NO_USB_DETECTION` set, no input is listed and none is opened, **even one saved in a station** (unlike a saved serial port): the station logs without audio and says `audio input disabled by NOCTULE_NO_USB_DETECTION` (`DisabledLineInSource`; the status bar reads `Line-in blocked`).
- **`NOCTULE_TEST_LINE_IN=<path>`** (test-only) puts the mock's `--line-out` socket in place of every line-in station's device, through the same pipeline. `noctule` honours it only with the kill-switch set, and the app only with the kill-switch and a private `NOCTULE_SETTINGS_DIR` (`LineInDetection`; otherwise the app prints `NoctuleScan: test override: ignoring NOCTULE_TEST_LINE_IN: it needs a private NOCTULE_SETTINGS_DIR and NOCTULE_NO_USB_DETECTION`). In effect it prints `test override: NOCTULE_TEST_LINE_IN=<path> (in place of the line-in device)` (`noctule: …` on the command line); `audio-inputs` then lists none and `station add --audio-input` saves its value as an ID. The mock's socket serves one client at a time, so give only one process `NOCTULE_TEST_LINE_IN`.
- **The microphone permission.** A development build is signed ad hoc, so macOS may ask again after a rebuild; on the command line the permission belongs to the terminal app that runs `noctule` (the agent's own host included), and a denial prints `warning: this terminal isn't allowed to use audio input. Allow it in System Settings › Privacy & Security › Microphone.` (`log` goes on without audio; `listen` ends with `audio: failed: <that sentence>`, exit 1). **The person you work for answers that prompt, never an agent.** An agent's `noctule log` or `noctule listen --station` on a line-in station without the kill-switch would open the real input, record the room and show the prompt: **always set the kill-switch for them, pass `--settings-dir` on a temporary directory, and give `NOCTULE_TEST_LINE_IN` only the mock's `--line-out` socket.**

## Build and test

Tests run against simulated scanners by default; tests against a real scanner are opt-in and read-only unless marked otherwise.

- `swift build` builds everything, including `noctule` and `noctule-mock-scanner`. Xcode schemes (`xcodebuild -list`): `noctule`, `noctule-mock-scanner`, `NoctuleKit`, `NoctuleStore`, `NoctuleAppCore`, `NoctuleScan` (the app), `NoctuleScan-Package`.
- `swift test` runs everything against the mocks and loopback fakes. Hardware tests are skipped, and so are tests marked `.skippedOnCIRunner("<reason>")` (`NoctuleKitTestSupport`) when `NOCTULE_CI_RUNNER` is non-empty. Only the workflows (`ci.yml`, `release.yml`) set it, for the tests the runner's three cores can't run reliably; an agent never sets it, so locally they run. **A test that can't run reliably on the CI runners takes that trait, never a `--skip` in a workflow** (beyond the existing split of timing-sensitive suites).
- `xcodebuild -scheme NoctuleAppCore -destination 'generic/platform=iOS' build` checks that the shared code builds for iOS (it covers `NoctuleKit`, `NoctuleStore` and `NoctuleAppCore`).
- Run tests in the foreground; give every new `@Suite` a `.timeLimit`.

### The kill-switch and test-only overrides

- **`NOCTULE_NO_USB_DETECTION`** (any non-empty value): `noctule` and the app find no USB ports anywhere (`ports` lists none, a bare `--serial` finds nothing and doesn't read `SCANNER_SERIAL`, `log` gives a USB station an empty listing) and list or open no audio input. A serial port is then opened only when its path is on the command line or saved in the station being run (`USBDetection`, shared with the app; SDS150 design §13 A, W). **Agents and tests always set it.** It does not cover a port saved in a station (see "Your saved settings" above).
- **`NOCTULE_TEST_SERIAL_PORTS`** (colon-separated paths, each listed as an SDS150; test-only): a decoy in place of the IOKit listing, so a build that ignored the kill-switch would find the decoy, never a real scanner. With detection on, `noctule` prints `noctule: test override: NOCTULE_TEST_SERIAL_PORTS=<paths> (in place of the system's serial port listing)`; with the kill-switch set it changes nothing. **Never point it at a real port.**
- **`NOCTULE_TEST_KEEPALIVE_SECONDS`** (0.05–60; test-only; **never set against a real scanner**): replaces the 60 s of a keep-alive the model already has (`KAL` or the renewal), for `watch --serial` and `log` on a USB station, so a test can run past `--push-lifetime`. `noctule` honours it only while the kill-switch is set (else `noctule: test override: ignoring NOCTULE_TEST_KEEPALIVE_SECONDS=<value> (it needs NOCTULE_NO_USB_DETECTION set)`), and prints `noctule: test override: NOCTULE_TEST_KEEPALIVE_SECONDS=<n> (…)` when in effect, or `… (not a number of seconds from 0.05 to 60)`. It can't make `noctule` send `KAL` to a model without a keep-alive, and does nothing on a network scanner (`KeepAliveOverride`). On the SDS100 mock keep it slower than the push interval (a faster renewal starves the pushes).
- Below the shells there is no default port listing: `StationTransportFactory`'s `ports` is required, and defaults pass `FixedSerialPortListing.empty`; only the `noctule` shell (through `USBDetection`) and the app's `AppDelegate` (through `SessionEnvironment.applyingOverrides`) pass the system's (`IOKitSerialPortFinder`; §13 L, W). Tests pass a fake listing, or get the empty one.
- **`NOCTULE_TRACE`** (any non-empty value; read-only diagnostics, honoured with the standard settings too; `CommandTrace`): `noctule` and the app write a command trace to stderr (`noctule: trace on (NOCTULE_TRACE)`, then `noctule: trace t=<ms> <event>`; the app `NoctuleScan: trace HH:MM:SS.mmm t=<ms> <event>`): `send`, `reply … after <n> ms`, `timeout`, `unmatched` (a reply nobody was waiting for), `push after …`, `serial: dropped …`, `quickkeys: …`. Lines hold command names, indexes, keys, counts, sizes and times, never a name, frequency or talkgroup (`CommandTraceTests`), so a trace can be shared. It changes nothing that is sent, so it may go on any run, a hardware run you were asked for included; run a new protocol path once with it and look for `unmatched` lines (LESSONS.md 2026-11-19).

### The command line

`noctule` reads a network scanner's address from git-ignored `config/dev-scanner.env` (`SCANNER_HOST`, `SCANNER_IP`, `SCANNER_RTSP_PORT`, `SCANNER_SERIAL`; see its `.example`) or `--host H [--port P]`; with no address it prints a hint and exits 2. Its parsing and formatting are in the `NoctuleCLICore` library (`StationCLI` holds `station`, `log` and `hits`); `Sources/noctule/` is the I/O shell. Exit codes: 130 on SIGINT, 143 on SIGTERM, 129 on SIGHUP, 64 on a usage error.

- **`info|status|display|menu|watch`** are read-only. `info`: model, firmware, volume, squelch. `status`: one `GSI`, one `label: value` line per field (`-` when missing), `signal` (`Sig`, what hit detection reads) and `muted`. `display`: one `STS` and the soft-key labels. `menu`: one `MSI`, the menu screen as data (outside a menu `type: error …`). `watch [--interval MS] [--count N]`: `MDL` first (exit 1 if no answer), then `PSI` updates until N lines or a signal; no update for max(5 s, 3 × interval), or an early end, prints why and exits 1. **It always sends `PSI,0` before exiting**, signals included.
- **`--serial [PATH]`** talks to a USB handheld instead (SDS150 design §5). `--serial PATH` (the next argument, when it starts with `/`) opens exactly that path, never a detected one (missing: `<path>: no such port`, exit 2). A bare `--serial` reads `SCANNER_SERIAL` (a path, used exactly; absent, empty or `auto`: automatic), else the one Uniden port found (none or several: a hint, exit 2). A busy port: `<path> is in use by another program.`, exit 1, nothing sent. Over serial `info` adds `battery: <n>% (<state>)` from one `GCS` (only to a model with `supportsChargeStatus`; no usable answer prints a warning and still exits 0), and `watch` sends the model's keep-alive (`KeepAliveOverride.forWatch`). Refused before anything is opened, exit 2: `--serial` with `--host` or `--port`, `listen --serial` (`no audio over USB`), `restart --serial`. **Agents pass `--serial` only the mock's path.**
- **`quick-keys [--host H] [--port P] | --serial [PATH]`** prints the Favorites tree, read-only (quick-keys design §5.3, §10): `MDL` first (a model without `supportsQuickKeys`, or one `MDL` doesn't name, prints `quick-keys: the <model> has no quick keys`, exit 1, nothing else sent), then `GLT,FL`, `FQK`, per keyed list `SQK` and `GLT,SYS`, per system `GLT,DEPT` (and `GLT,SITE` unless conventional), and `DQK` per keyed system of a keyed list (`QuickKeyTreeReader`; never a set, never `PSI`). Paged replies are put together first (`SerialResponseAssembler`). Format: `CLIFormat.quickKeys`, pinned in `QuickKeysFormatTests`.
- **`ports`** lists the Uniden serial ports from the IOKit registry (`<path>  <product name>  <model>`), or `No Uniden scanner found. …`; nothing is opened or sent. **`audio-inputs`** lists the Mac's audio inputs (`<UID>  <name>  <n> ch`) from Core Audio properties, opening no stream; under the kill-switch it lists none (`CoreAudioInputs` is never constructed). **Agents run `audio-inputs` only under the kill-switch.**
- **`listen [--record PATH] [--seconds N] [--no-play] [--host H] [--rtsp-port P] [--reconnect-cooldown S]`** streams the SDS200's audio over RTSP: one session, played unless `--no-play`, recorded as 16-bit 8 kHz mono WAV with `--record` (flushed every second); `SCANNER_IP` (else `SCANNER_HOST`) and `SCANNER_RTSP_PORT` (default 554). Status on stderr (`audio: streaming`, `audio: recovering (attempt N)`, `audio: failed: …`), `packets N  lost N  recoveries N` on stdout at exit; exit 0 after `--seconds`, 1 on failure. **Every exit path sends TEARDOWN and closes the WAV** before the process exits (a second signal only prints `audio: still closing the scanner session…`); SIGPIPE is ignored. On failure it prints a hint from a UDP `MDL` probe.
  - **Reconnect cooldown:** every RTSP close, clean or not, is recorded in `~/Library/Caches/NoctuleScan/rtsp-cooldown.json`; no connection within 120 s of the last unclean one, or within the clean-close wait of a clean one, across runs (`audio: waiting <n> s before reconnecting (scanner cooldown)`; a signal during the wait exits with no connection). **Don't delete the file to skip the wait.** The check and the connection's lease are one atomic claim under the file's `flock`, so two processes can't both connect; if the lock can't be taken the CLI refuses to connect (`cooldownStoreUnavailable`).
  - `--cooldown-seconds N` and `--cooldown-store PATH` are for the mocks and loopback fakes only: `--cooldown-seconds` sets the full value. `listen` and `log` refuse `--cooldown-seconds` (exit 2, nothing sent) unless `--cooldown-store` names a private file, not the shared record (compared after resolving symlinks).
  - **`listen --station <name> [--meter]`** (line-in design §12.4; `ListenStation`): the station supplies the flags, reading the settings and writing nothing. **On a USB station with a line-in** it opens only the audio input: no serial port, no `StationLock`, no scanner traffic, no RTSP, no cooldown record, no hit log; a missing input, or a failure after the input has streamed, is a wait, not a failure; it exits 1 with `audio: failed: <reason>` when the source fails before ever streaming (the kill-switch included) or on a denied permission. `--meter` draws a one-line text meter on stderr (`LineInTextMeter`; redrawn in place on a terminal, one plain line a second otherwise). **On a network station** it runs RTSP as above, with the station's address and reconnect wait. Its lines and refusals are pinned in `LineInCLIIntegrationTests`.
- **`restart [--yes]`** sends `MSM,1` to an SDS200 over the network, waits for `MDL` to answer again, prints how long the reboot took, clears the scanner's cooldown record, and notes that whether a restart revives a wedged audio server is unverified. Without `--yes` it asks `Restart the scanner at <host>? [y/N]`. **It changes scanner state: run it only when the person you work for asks.**
- **`station add|list|remove`** manages stations (`stations.json`, `device.json`, `app.json`); it never talks to a scanner. Only a missing file reads as empty: one that can't be read, or is undecodable and can't be moved aside to `<name>.corrupt-<stamp>`, makes `station`, `log` and `hits` print `can't read <path>: <reason>; nothing was changed` and exit 1 without writing.
  - `station add --name N --host H [--udp-port P] [--rtsp-port P] [--save-audio every|new|never] [--reconnect-cooldown S]`: checked by `Station.validate()` (a wait outside 0–120 reads as 120); names are unique, case-insensitively. `--reconnect-cooldown` (0–120, default 120) is the person's setting.
  - `station add --name N --usb [--serial-port PATH]`: no host, ports or reconnect wait (`--usb` refuses them). `--serial-port` is saved as the station's `usbPort` in `device.json`, before the station; when run, that port is used and no other (a saved port that isn't there is "not plugged in"; SDS150 design §13 Q). With none saved, the only Uniden port found (none under the kill-switch).
  - `station add … --usb --audio-input <UID or name> [--audio-channel left|right|both]` gives a USB station its line-in (line-in design §12.4): a listed input's UID, or a name matching exactly one listed input. **Where no inputs are listed** (the kill-switch, or `NOCTULE_TEST_LINE_IN`) a value is saved as a UID, with `station: saved "<x>" as an audio input ID (no inputs are listed)`: that is how tests and agents give a station an input. `station` queries Core Audio only for an `--audio-input` value, and never under the kill-switch.
  - `station list` marks the last used station with `*`; `station remove --name N` keeps its hit log and recordings.
- **`log [--station N] [--seconds S] [--recordings DIR]`** runs one station (`StationRunner`: `PSI` pushes, hit detection, the hit log in `…/Stations/<uuid>/hits.sqlite`, and on a network station one RTSP session and a WAV per transmission in `~/Music/Noctule Scan/<station name>/`). It prints `HH:MM:SS  + TG9 Lakeview Fire  (new)` when a hit starts and `HH:MM:SS  - TG9 Lakeview Fire  2.3 s  → <file name>` when it ends; status and `warning:` lines go to stderr. Without `--station`, the last station `log` ran, else the only one.
  - It stops after `--seconds` or on a signal, always through `runner.stop()`: `PSI,0`, TEARDOWN, open hits closed and logged (a second signal only prints `log: still closing the scanner session…`).
  - On a network station it respects the reconnect cooldown through the same record as `listen`, waiting before it sends anything to the scanner (with `--save-audio never` it doesn't wait); if audio can't start it warns and logs hits without audio. A transmission already on air when audio starts is recorded from then, with no pre-roll.
  - **On a USB station:** no cooldown wait and no cooldown record, ever. Without a line-in, no audio (`log: no audio over USB`); with one, a WAV per hit and the line-in warnings (`audio: line-in <name> (<channel>)`; under the kill-switch `warning: audio input disabled by NOCTULE_NO_USB_DETECTION` and no audio). Every subscription sends the model's keep-alive; a failed keep-alive write, or a renewal the SDS100 refuses, prints `warning: couldn't send the keep-alive (…); status updates may stop` once per subscription. **A subscription that stops pushing is replaced** once per connection (SDS150 design §13 V: `warning: the scanner stopped sending status updates; subscribing again`, `PSI,0`, the port closed, a fresh `PSI`). A missing port at start fails at once with the plug-in or several-ports hint, a busy one with `<path> is in use by another program.` (exit 1). When the scanner goes away mid-run, open hits are logged, `log` waits (looking for the port every second, opening nothing) and resumes when the same model answers `MDL` (§13 J, N), with a bounded number of probes per appearance of the port (§13 H); a connection that never delivered a push isn't resumed (§13 F: `warning: the scanner isn't sending status updates; not reconnecting by itself`, exit 1).
  - **Recordings and hit logs made against a real scanner are real radio traffic.** Never commit them; delete test recordings after a hardware check.
- **`hits [--station N] [--groups] [--new] [--since YYYY-MM-DD] [--csv]`** reads a station's hit log (`*` marks new rows; `--csv` writes every matching transmission).
- `station`, `log`, `hits` and `listen --station` take `--settings-dir DIR` (and `log` takes `--recordings DIR`); the hit logs follow `--settings-dir`. **Agents always pass it.**

### Hardware tests (opt-in)

All are skipped by default; run them only when the person you work for asks, against their scanner, and never set these variables on your own.

- `NOCTULE_HARDWARE_TESTS=1 swift test --filter HardwareTests`: read-only checks against the network scanner in `config/dev-scanner.env` (one of them sends one `GSI`, then at most one `MSI`, and nothing if the scanner is in a menu; none sends `KEY` or `MSV`). The filter also matches the handheld suites, which stay skipped without their own variables. `NOCTULE_RESTART_HARDWARE_TEST=1` sends `MSM,1`. `NOCTULE_AUDIO_HARDWARE_TESTS=1 swift test --filter AudioHardwareTests`: at most two RTSP sessions, at least 120 s apart, both torn down.
- `NOCTULE_SDS150_HARDWARE_TESTS=1 swift test --filter SDS150HardwareTests` (and `NOCTULE_SDS100_HARDWARE_TESTS=1 … SDS100HardwareTests`): the read-only suite (`MDL` must name the expected model, else nothing more is sent; then `VER`, `VOL`, `SQL`, `GSI`, `STS`, one each; the `STS` lines' widths are printed, never their text; the SDS100's also reports whether `GSI` has `Battery`) and **the quiet-port check** (`…/QuietPort`: opens the port and sends **nothing at all** for 2 s, failing if a `PSI` document arrives, which means an earlier `PSI,0` didn't take effect). The quiet-port check is how to look at a port. Adding `NOCTULE_SDS150_PUSH_TEST=1` (`NOCTULE_SDS100_PUSH_TEST=1`) runs the push suite (`PSI,500`, 20 `GSI`s, `PSI,0` on every path, then a 1.5 s hold in which no push may arrive more than 250 ms after `PSI,0`). `NOCTULE_SDS150_KEEPALIVE_TEST=1` runs the 4-minute keep-alive check (`PSI,1000`, `KAL` every 60 s, held 240 s; fails if 5 s pass without a push); `NOCTULE_SDS100_KEEPALIVE_TEST=1` the same with the `PSI,1000` renewal, and `NOCTULE_SDS100_KEEPALIVE_100MS_TEST=1` at the product's rate (`PSI,100`). None sends `GCS`, `KEY`, `MSV`, `MSM` or `POF`, and the SDS100's never `KAL`. All are skipped while `NOCTULE_NO_USB_DETECTION` is set, decided before any port is resolved; they open `SCANNER_SERIAL` (`SCANNER_SERIAL_SDS100`) from `config/dev-scanner.env` exactly as written, else the one port whose USB product name names the model (`HandheldHardwareChecks.resolvePort(for:)`; none or several fails, opening nothing). The checks live in `Tests/NoctuleKitTests/HandheldHardwareChecks.swift`, and their mock twins (`…/OnTheMock`, `KeepAliveOnTheMock`) run in every `swift test`, pinning exactly what each sends. SDS150 design §8 and SDS100 design §5.6, §7 describe them.

### Branding

The official icon and installer art are not in this repository (open-source prep design §4); local builds use committed placeholder art: `Resources/Placeholder/AppIcon.icon` and `packaging/dmg/placeholder/` (`background.tiff`, drawn by `render-placeholder-background.swift`).

- **`NOCTULE_BRANDING_DIR`** chooses the art (`scripts/branding.sh`, sourced by `compile-app-icon.sh` (which `build-app.sh` runs), `make-dmg.sh` and `release.sh`): set to a folder holding `AppIcon.icon` and `dmg/background.tiff`, that folder (anything else fails the build); set but empty, the placeholder, and `config/branding.env` isn't read; unset, `NOCTULE_BRANDING_DIR` from the git-ignored `config/branding.env` (template `config/branding.env.example`; a relative path counts from the repo root), else the placeholder. Each script says which on stderr (`branding: <path>` or `branding: placeholder (set NOCTULE_BRANDING_DIR for the official art)`).
- **Every test that runs `compile-app-icon.sh`, `make-dmg.sh`, `build-app.sh` or `release.sh` sets `NOCTULE_BRANDING_DIR`** (empty, or a stub folder), so a developer's `config/branding.env` never reaches a test (`BrandingTests`, `AppIconCompileTests`, `AppIconBuildScriptTests`, `PackagingTests`).
- `packaging/branding-ref` pins the design-language commit an official release uses (packaging/README.md). `release.sh` refuses an official (tagged) release without the art; an `--untagged` build on the placeholder is named `…-untagged-unbranded.dmg`.
- `scripts/compile-app-icon.sh` compiles the icon with `actool` into the bundle's `Assets.car` and `AppIcon.icns`, and fails if the icon's name isn't the one `Info.plist` gives (`AppIcon`). Edit an icon in Icon Composer (`/Applications/Xcode.app/Contents/Applications/Icon Composer.app`), the only place to check its Dark, Clear and Tinted appearances. macOS caches icons: after a change, `touch` the bundle (or `killall Dock`) before judging it.

### Releases (maintainers)

Releases are built, signed and notarized by `.github/workflows/release.yml` from a `vX.Y.Z[-suffix]` tag a maintainer pushes on `main` (packaging/README.md "Releases from a tag"; release manager design `docs/specs/2026-11-14-release-manager-design.md`; Plans 12–15). The job tests, signs with the `NOCTULE_*` secrets of the GitHub Environment `release` (deployment rule: `v*` tags only), notarizes, and drafts a GitHub Release a maintainer publishes. **A tag push sends the app to Apple.**

- **Agents never push a `v` tag, create or publish a release, or run the release workflow; never run `packaging/cut-release.sh`, `packaging/release.sh`, `packaging/notarize.sh <file>` or `packaging/ci/release-from-tag.sh` for real** (only through the tests' stubs and fake repositories: `PackagingTests`, `CutReleaseTests`, `MakeDMGTests`); and **never create, export, read, print, set or move signing certificates, `.p12` or `.p8` files, their IDs, deploy keys, or the environment's secrets.**
- `packaging/notarize.sh --check` finds the certificate and credentials without sending anything. `release.sh <version> [--build N] [--allow-dirty] [--untagged]` refuses a `HEAD` that doesn't carry `v<version>` (`--untagged` allows a local try), stamps the version into the built bundle (the tracked `Info.plist` stays `0.0.0`), and checks the app inside the finished DMG. `release-from-tag.sh --preflight <tag>` runs only the checks that need no Apple secret. `cut-release.sh beta|final|patch|minor|major [--beta] [--first X.Y.Z[-beta.N]]` is a maintainer's one command for cutting a release (`CUT_RELEASE_POLL_SECONDS` and `CUT_RELEASE_POLL_LIMIT` are test-only).
- The DMG's window (Plan 13, `docs/specs/2026-11-14-plan-13-installer-window.md`) is made by `packaging/dmg/make-dmg.sh` with `dmgbuild` and `packaging/dmg/settings.py`, from a venv in `build/dmg-venv` (hash-pinned wheels from PyPI, installed on first use; Python 3.10+, `NOCTULE_PYTHON` or `python3`; `NOCTULE_DMG_VENV` moves it; `--prepare` only builds it). `MakeDMGTests` install it once per run and so need the network. `PackagingTests` run every script against stub `codesign`, `xcrun`, `spctl` and `security`; its suites that make disk images run one test at a time (LESSONS.md 2026-11-13). The release run has time limits (`timeout-minutes`; `.timeLimit` on every suite of `NoctuleCLIIntegrationTests` and `NoctuleMockScannerTests`).

## The Mac app

The `NoctuleScan` executable target (SwiftUI + AppKit, macOS only; sources under `#if os(macOS)`) holds only views and the AppKit shell; the platform-neutral logic (`StationSession`, `MenuModel`, `QuickKeysModel`, `SessionRegistry`, `DisplayModel`, `KeyboardRouter`, `KeyPressQueue`, `DisplayRefreshPolicy`, `HitLogModel`, the settings models) is the `NoctuleAppCore` library, which builds for iOS (no AppKit, UIKit, SwiftUI or AVFAudio). `scripts/build-app.sh [debug|release]` assembles `build/Noctule Scan.app` (git-ignored) from `Resources/Info.plist` (bundle id `app.noctule.scan`, unsandboxed, ad-hoc signed with the hardened runtime and `Resources/NoctuleScan.entitlements`, which holds the audio-input entitlement; `Info.plist` has the microphone usage string); check it with `codesign -dv "build/Noctule Scan.app"`. Every session warning is also written to stderr as `NoctuleScan: HH:mm:ss warning: <station>: <text>` (`SessionWarningLog`), so a run launched from Terminal with `2> file` keeps a record.

### Launching it

- **It uses the same files as the CLI**, so launched without overrides it talks to the stations saved there, which may be a real scanner, and opens the last station by itself (its audio, or its serial port).
- **Never launch the app (or `NoctuleScan` from `swift build --show-bin-path`) without `NOCTULE_SETTINGS_DIR` pointing at a temporary directory whose only stations are mocks (the network mock on 127.0.0.1, or a USB station whose saved port is the serial mock's `--serial-link` in that directory), and `NOCTULE_NO_USB_DETECTION=1`**, unless the person you work for asks for a run against their scanner.
- **Test-only environment overrides**, for runs against the mocks only: `NOCTULE_SETTINGS_DIR` (settings, hit logs, station locks), `NOCTULE_RECORDINGS_DIR`, `NOCTULE_COOLDOWN_STORE`, `NOCTULE_COOLDOWN_SECONDS` (the full value; a station's clean-close wait is clamped to it) and `NOCTULE_TEST_PRESENT_SHEET` (each station window presents a sheet once its session is open). All but the first need `NOCTULE_SETTINGS_DIR`; the store and the seconds only when that isn't the standard `~/Library/Application Support/NoctuleScan`, and the seconds only with a `NOCTULE_COOLDOWN_STORE` that isn't the shared record (paths compared after resolving symlinks); otherwise the app prints `ignoring …` and keeps 120 s. The app prints each one in effect (`NoctuleScan: test override: …`). For USB (`SessionEnvironment.applyingOverrides`; SDS150 design §13 W): `NOCTULE_NO_USB_DETECTION` (honoured always, printing nothing); `NOCTULE_TEST_SERIAL_PORTS` (a decoy, honoured only with a private `NOCTULE_SETTINGS_DIR` and the kill-switch unset, which an agent never leaves unset); `NOCTULE_TEST_KEEPALIVE_SECONDS` (honoured only with **both** a private `NOCTULE_SETTINGS_DIR` and the kill-switch, since a private directory can hold a copied station whose saved port is a real scanner). **The app's port listing** (used only by a USB station with no saved port, and by the editor) is the system's only with the standard settings directory and the kill-switch unset; with a private directory, the decoy if given, else empty. A saved port is opened whatever the listing says. **Never point the app at a real scanner with a shortened cooldown**, and never lower a real station's reconnect wait yourself.
- **On the network mock by hand:** `scripts/build-app.sh`; `swift run noctule-mock-scanner --verbose --cooldown-seconds 20` (add `--cooldown-after unclean` to try a reconnect wait below 20 s); with `D` a fresh temporary directory, `noctule station add --settings-dir "$D/settings" --name Mock --host 127.0.0.1 --udp-port <udp> --rtsp-port <rtsp>`; optionally write `{"version":1,"lastStationID":"<its id from stations.json>"}` to `$D/settings/app.json` so it opens at launch; then `NOCTULE_SETTINGS_DIR="$D/settings" NOCTULE_RECORDINGS_DIR="$D/recordings" NOCTULE_COOLDOWN_STORE="$D/cooldown.json" NOCTULE_COOLDOWN_SECONDS=20 NOCTULE_NO_USB_DETECTION=1 "build/Noctule Scan.app/Contents/MacOS/NoctuleScan"` (launching the binary directly passes the environment and keeps its stderr). Quit it with ⌘Q or `osascript -e 'tell application id "app.noctule.scan" to quit'`, Ctrl-C the mock, and check `leaked-sessions=0`. Delete `$D` afterwards.
- **A USB station on the serial mock by hand:** `export NOCTULE_NO_USB_DETECTION=1` and `D=$(mktemp -d)`; `swift run noctule-mock-scanner --model sds150 --serial --serial-link "$D/port" --verbose` (`--model sds100` for an SDS100, whose renewals show as `PSI,100` in place of `KAL`; `--fault unplug=20:15` to see the waiting banner and the resume; for a line-in, `--line-out "$J/jack.sock"` with `J=$(mktemp -d)`, `"audioInputDevice": "fictional-input-1", "audioInputName": "Fictional Interface", "audioInputChannel": "left"` beside the station's `usbPort` in `$D/settings/device.json`, and `NOCTULE_TEST_LINE_IN="$J/jack.sock"` on the app's command line); `noctule station add --settings-dir "$D/settings" --name "Mock 150" --usb --serial-port "$D/port"`; write `app.json` as above; then `NOCTULE_SETTINGS_DIR="$D/settings" NOCTULE_RECORDINGS_DIR="$D/recordings" NOCTULE_NO_USB_DETECTION=1 "build/Noctule Scan.app/Contents/MacOS/NoctuleScan"`. Quit it, Ctrl-C the mock, and check `active-subscriptions=0`, that the mock's log ends with `PSI,0` and holds no `MSM` or `POF` (on an SDS100, no `KAL` or `GCS` either). Delete `$D` afterwards.
- **Pictures:** of the app's window only, by window id (`screencapture -x -o -l <id>`, the id from `CGWindowListCopyWindowInfo` for the app's pid), never the full screen (LESSONS.md 2026-11-13). Screenshots for the README go in `images/screenshots/` under that folder's own terms, taken on the mocks with no real values.
- **Driving the app** with computer-use tools (`request_access` for `app.noctule.scan` first): the same launch rules apply (mocks only, a temporary `NOCTULE_SETTINGS_DIR`, the kill-switch). It is layered on top of the developer, QA and mutation checks, not in place of them, and every action is checked against the mock's `--verbose` log (one `KEY`, `VOL`, `MSV` or quick-key set per action, a system's, department's or site's switch after its pre-set `GLT` reads, `PSI,0` and `leaked-sessions=0` or `active-subscriptions=0` at the end). Quit from the app's menu (⌘Q needs a grant agents don't ask for). It needs Accessibility for the app that hosts the agent's terminal and a restart of that terminal (LESSONS.md 2026-11-13), and can't click while macOS Full Keyboard Access is on (ask the person to turn it off). The attached Quick Keys pop-over is `.transient`: bring the app forward before acting on it. Press keys with the `key` action: `type` reaches none of the app's key monitors, and the `key` action's `escape` reaches no monitor at all, so Esc is the person's to press (LESSONS.md 2026-11-18). Hand checks listed in the plans can be run this way on the mocks.

### Sessions and stations

- **One session per station per process** (`SessionRegistry`), and **one process per station** (`StationLock`, `flock` on `Stations/<uuid>/runner.lock`, shared with `noctule log`: a second process gets "<name> is open in another Noctule Scan process (pid <n>)."). **One scanner has at most one open session per process** (`SessionRegistry.ScannerIdentity`: a network station's host, UDP and RTSP ports; a USB station's saved port, an automatic one conflicting with every USB station; SDS150 design §13 AA): a second station on the same scanner shows "<other station> is already connected to this scanner." and opens nothing. Two processes on two different stations with the same address are not prevented (for USB the port's exclusive open refuses the second).
- Edits: view, key map, colors, saved filters and counts apply live, and a change to the reconnect wait alone is taken at the next start; any other edit (name, connection, recording rules, a USB station's saved port) restarts the open session (`SessionRegistry.restartRelevant`, `deviceSettingsChanged`): TEARDOWN, then the station's wait if that TEARDOWN was answered, 120 s otherwise (no cooldown for USB). Changing the wait during a cooldown wait doesn't shorten it. Switching between the Scanner and Mac-style views never restarts the session (`StationViewPreference`).
- **A USB station** (SDS150 design §7, §13 Q–AC; `StationSession+USB.swift`): no cooldown gate, never a call on the cooldown store. While its port isn't there the phase is `.waitingForScanner(hint:)`, polling every second and opening and sending nothing; once it is, it runs the same `StationRunner` as `noctule log` (`PSI,100`, the model's keep-alive, the resubscribe rule), with no audio unless a line-in is set. The display reads `STS` at most once per `displayRefreshInterval` (100 ms on the SDS200, SDS150 and SDS100, 1 s otherwise; §13 AC). A busy port, a scanner that doesn't answer, or any other start failure is `.noAnswer(…)`, and **no USB start failure is retried by itself** (§13 Z): only Reconnect, or the next wake, opens the port again. `GCS` is sent once at connect and every 60 s only to a model with `supportsChargeStatus`. `restartScanner()` refuses any station that isn't a network station, before anything is stopped or sent. Test Connection on a USB station sends `MDL` and `VER` only, on a fresh transport always closed afterwards, and opens nothing while the station's own window is open. The editor saves no port unless the user picks one (§13 X). A Bluetooth station, or a USB station on iOS, ends in `.noAnswer("This kind of connection isn't supported on this device yet.")` with nothing opened.
- The windows, the picker and the editor are described in the SDS150 design §7 and the Mac app plan (`docs/specs/2026-11-09-plan-4-mac-app.md`); the station picker reopens the last station that reached `.connected` at launch (`app.json`).

### Keys, menus and quick keys

- **Keyboard** (`KeyRouting`): a local key-down monitor acts only for its key window and consumes every key it presses (both monitors install `LocalKeyMonitor.forward(event, to:)`; LESSONS.md 2026-11-18); a focused text field or key-taking view (or a control marked `.tracksKeyboardFocus()`), unmapped chords and menu key equivalents pass through; only the scroll keys repeat. **While the Mac-style view shows a menu, the monitor never presses a mapped key**: ↑ ↓ Return Esc go to the menu when its handler is installed, and every other mapped chord is swallowed (`KeyRouting.decide(…, macMenuShowing:)`). **While the Quick Keys pop-over is attached**, its own monitor takes every key from the station window (digits pick a tile, Space and Return toggle it, ⌘↓ opens its tree, ⌘F the search, Esc closes it, menu key equivalents pass, everything else goes nowhere), and the station window's monitor steps aside (`StationShortcuts`; quick-keys design §10).
- **Menus** (remote menus design §5; `MenuModel`, `session.menu`): the Scanner view mirrors the scanner's menu; the Mac-style view shows it as native controls (a list, an entry field, or the mirrored text for a screen `MSI` can't describe). Menu state comes only from the model's reads (about every two seconds and after each action), never from pushes. Hold and Avoid are disabled in a menu; destructive items (`ModelProfile.destructiveMenuItems`) ask inline first, and Cancel sends nothing; key-repeat activations never send.
- **Menu action rules** (`MenuModel`; remote menus design §5.4–§5.5): **one action sends at most one `KEY` or `MSV` and never resends.** Actions are refused (`.busy`) while another is in flight, re-check and re-read included; background refresh reads don't block actions, and their results are dropped if an action started meanwhile. Before every `MSV` the model re-reads `MSI` and sends only if the menu index, the item's index and its name still match (else `.menuChanged`, nothing sent); `setValue` also needs the same `Value` the user edited, and validates against the re-read screen's rules. `enter()` reads `GSI` first and sends the Menu key only if not already in a menu; `exit()` sends `KEY,L,P` only if `GSI` says the scanner is still in one (outside a menu that key is Avoid; an unanswered `GSI` sends nothing). A confirmed destructive Enter reads a fresh `STS` first and is sent only if the highlighted row is still the confirmed one. Accepted residual windows: replies match requests by command name, so a late `MSI` reply can answer a later read, and the radio's panel can move the highlight between the `STS` and the `KEY,E,P`.
- **Quick Keys** (quick-keys design §5.4, §5.5, §10; `QuickKeysModel`, `session.quickKeys`): a toolbar pop-over (or a torn-off panel) with the keypad and each list's tree. It sends nothing while closed; opening reads `GLT,FL` and `FQK`, then each list's tree in the background (a timed-out background `GLT` read is sent again once); while open it re-reads `FQK`, the open list's `SQK` and its systems' `DQK` every 2 s. Clicks follow the set rules under "Your scanner" (a set answered anything but `OK` shows `The scanner didn't confirm the change`). Every switch and tile is disabled while the scanner is in a menu; no system, department or site switches until every keyed list has been read since the pop-over opened or the scanner left a menu; a `GLT` reply naming an item another parent is known to hold is refused as a late reply. A row whose list or system key is shared shows its state but doesn't switch (open: GitHub issue #1). Every stop quiesces it before `PSI,0`.
- **The quick-key cache** (`Stations/<uuid>/quick-keys.json` in the settings directory; structure only, never a state) **holds the user's real list and system names**: never copy or commit one.

### Lifecycle guarantees

- **Quit** (⌘Q, an AppleEvent quit, or SIGTERM, SIGHUP, SIGINT) waits for every session to stop (`PSI,0`, TEARDOWN), sessions still stopping after a window close or an edit included, for at most 15 s, then exits 0; if AppKit refuses the quit because a sheet, alert or panel is open, a signal still stops every session and exits 0.
- Closing a station window releases its session. A session the registry lets go of is retired: nothing (a Reconnect still tearing down, a wake, a restart) can start it again. A user stop during a Reconnect's or a wake's wait wins over its start.
- **The app never opens a new audio session on its own after audio `.failed`**: only Reconnect or Restart scanner (after its confirmation dialog) does; it opens one automatically only when a window opens and after a wake, always through the cooldown gate.
- **Sleep** (`SystemPowerObserver` + `PowerGate`) holds the Mac awake until every session has suspended (`PSI,0`, TEARDOWN; a USB session closes its port), for at most 20 s; a full wake (`NSWorkspace.didWakeNotification`, not a dark wake) resumes them through the cooldown gate (USB with none). A network station's no-answer after a wake is retried on a backoff (5, 10, 20, 30 s, then every 30 s); a USB station's failed start never is.
- **Every stop first stops the key queue**, before any await, so keys still queued from the Scanner view are dropped, not sent.
- `AppLifecycleIntegrationTests` launches the built app on the mocks with these overrides (network: SIGTERM and SIGHUP, with a sheet open, with the scanner in a menu; USB: tear-down, waiting for the scanner, resume after a replug, keep-alive on both models) and checks TEARDOWN, `PSI,0` last, `leaked-sessions=0` or `active-subscriptions=0`, no `MSM`, `POF`, `KEY` or `MSV` it didn't send itself, no cooldown file for USB, and exit 0 within 15 s. It shows the app's window for a moment.
